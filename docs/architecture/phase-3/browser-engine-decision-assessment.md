# Browser engine decision assessment

**Assessment date:** 2026-11-07. **Phase 4.2 owner disposition:** Phase 3 closure APPROVED; WKWebView CONDITIONAL ACCEPTANCE for MVP planning and implementation; architecture baseline APPROVED. ADR 0001 remains Proposed.

See the [owner approval decision](owner-approval-decision.md) and [Phase 5 preparation](../phase-5/README.md). The analysis below records the original pre-approval recommendation and alternatives; its earlier “unapproved/pending” wording is historical, not the current owner decision. Evidence/limitations are unchanged. Conditional acceptance is not unconditional production-engine or release approval, and this task begins no implementation/build/test.

## Historical Phase 4 recommendation (retained analysis)

Recommend **Option 1: conditional acceptance of WKWebView as the macOS MVP engine for planning**, paired with the engine-independent baseline. This is an engineering judgment from bounded native integration evidence and lower initial runtime-packaging ownership, not proof of complete website compatibility, secure product implementation or release performance. It becomes a decision only after explicit product-owner acceptance of the unknowns and the staged gate policy in [ADR 0001](../../decisions/0001-browser-engine-strategy.md).

Close the continuous Phase 3 testing loop as a documented feasibility investigation. Do not start production or new validation from this recommendation. If the owner cannot accept unverified critical authentication/workflows before choosing an engine, select Option 2 with a finite, separately approved scope instead of an open-ended “continue testing” instruction.

## Conditions for approval and non-waivable safeguards

1. **Bounded closure:** accept the recorded investigation and the A/B/C/D split; do not rename partial or untested requirements Passed.
2. **Compatibility risk:** identify launch-critical workflows and accept their unknown status for engine planning, or choose Path 2. Public pages and synthetic auth cannot substitute for account evidence.
3. **Staged sequencing:** explicitly approve moving product implementation and release gates to their proper milestones. Earlier maintained criteria currently link broad product gates to selection; the proposed ADR changes sequencing, not their required outcomes.
4. **Architecture baseline:** approve the ownership/trust boundaries and explicit freeze exceptions below. No raw engine objects, generic script/reflection, arbitrary paths or page-originated privileged commands across the chrome bridge.
5. **Hard failures remain hard:** an observed cross-profile/private leak or unauthorized action requires remediation and evidence; no blanket owner risk acceptance makes such a defect Passed.
6. **Release obligations remain:** macOS 26.0/latest supported 26.x, Developer ID/notarization, minimal release entitlements, clean install, compatibility/performance qualification and ADR 0002 update integrity are required at their applicable stage.
7. **Separate authorization:** implementation, additional account/media tests and any CEF proof of concept require a new scoped instruction. This review ends after preparation.

## Vendor facts versus engineering inferences

WebKit publishes website-data-store and navigation-delegate API surfaces; their existence supports an adapter design, while Vezham behavior claims above come from local evidence. Public headers are not validation of the installed macOS 26 runtime or a promise of per-profile OS process isolation. [WebKit website-store header](https://raw.githubusercontent.com/WebKit/WebKit/main/Source/WebKit/UIProcess/API/Cocoa/WKWebsiteDataStore.h), [navigation delegate header](https://raw.githubusercontent.com/WebKit/WebKit/main/Source/WebKit/UIProcess/API/Cocoa/WKNavigationDelegate.h).

CEF is a Chromium embedder. Its project documents application-owned updates and possible build lag; its macOS layout includes an engine framework and helper app, with OS-specific sandbox setup. We infer additional Vezham integration/release ownership from those requirements; no Vezham CEF feasibility, performance or compatibility result is claimed. [CEF README](https://github.com/chromiumembedded/cef/blob/master/README.md), [application layout](https://chromiumembedded.github.io/cef/general_usage.html#macos), [sandbox setup](https://chromiumembedded.github.io/cef/sandbox_setup#macos).

No exact CEF size, version choice, performance advantage, universal extension support or legal clearance is asserted. Pin implementation references and review exact dependency notices before any separately approved evaluation or release.
