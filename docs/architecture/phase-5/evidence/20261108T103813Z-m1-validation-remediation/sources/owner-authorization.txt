# 3. EXP-01 — WebKit store cleanup diagnosis

## 3.1 Failure context

The previous experiment reported:

- Persistent profile isolation observations succeeded.
- Cross-profile sharing observations succeeded.
- Relaunch observations succeeded.
- Store removal failed while references remained live.
- A cleanup-only follow-up crashed after boot.
- Cleanup completion for two disposable synthetic stores is unknown.
- No unchanged retry loop was executed.

Treat the failure and unknown cleanup state as unresolved.

## 3.2 First phase: read-only diagnosis

Before performing any cleanup operation:

1. Inspect the original experiment report.
2. Inspect the cleanup-only follow-up report.
3. Inspect available crash logs and diagnostic output.
4. Identify the two synthetic store locations, if recorded.
5. Determine their ownership and whether they are still referenced by a running process.
6. Identify the relevant WebKit configuration and lifecycle code used by the experiment.
7. Identify every retained object, view, website-data store or process reference that could prevent removal.
8. Determine whether the previous crash occurred before, during or after the removal operation.
9. Determine whether the cleanup operation may have partially completed.
10. Determine whether any test artefacts are still needed as evidence.

Do not infer cleanup success from a missing directory alone.

Do not infer cleanup failure solely from an old crash report.

Do not delete anything during this phase.

## 3.3 Second phase: classify store state

For each synthetic store, report one of:

- Confirmed present and intact.
- Confirmed present but partially modified.
- Confirmed removed.
- Confirmed removal incomplete.
- State unknown.
- Inaccessible or unable to inspect safely.

Include the evidence supporting each classification.

If the original paths cannot be established, state that the store identity is unknown.

Do not search broadly and delete similarly named directories.

## 3.4 Third phase: identify the root cause

Investigate possible causes without assuming any one is correct:

- Live WKWebView references.
- Retained WKWebsiteDataStore references.
- Active navigation or website-data operations.
- WebKit process lifecycle.
- Incorrect teardown ordering.
- Asynchronous removal completion.
- Application termination or crash timing.
- Operating-system/WebKit behaviour.
- Incorrect test harness assumptions.
- Other evidence-supported causes.

Distinguish:

- Confirmed root cause.
- Contributing factor.
- Plausible hypothesis.
- Unknown.

Do not label a hypothesis as a confirmed root cause.

## 3.5 Fourth phase: bounded diagnostic verification

Only after the state of the original synthetic stores is understood:

- Use newly created disposable synthetic stores for any fresh diagnostic verification.
- Record the exact macOS version and hardware architecture.
- Record the WebKit configuration.
- Record all creation and teardown steps.
- Establish an explicit reference-release sequence.
- Verify asynchronous operation completion.
- Capture crash and error evidence.
- Confirm the final state of each new synthetic store.

Do not rerun the unchanged failed procedure in a loop.

Do not attempt to remove an original store with unknown ownership or state.

If a cleanup operation cannot be shown safe, stop and report it.

## 3.6 EXP-01 conclusion

Provide:

- Confirmed root cause or unresolved diagnosis.
- Evidence.
- Store-by-store state.
- Whether the original experiment result remains FAIL.
- Whether a narrowly scoped follow-up result changes any specific finding.
- Remaining limitations.
- Required engineering changes as proposed tasks only.

Do not silently convert the original EXP-01 FAIL to PASS.

A follow-up can qualify a specific remediation without erasing the original failure history.

# 4. Persistent-profile encryption specification closure

Review OD-R07, OD-R08, OD-R09, OD-R18 and OD-R19 alongside:

- REQ-06, REQ-07, REQ-08 and REQ-22.
- SPEC-05, SPEC-07 and SPEC-08.
- EXP-03, EXP-04 and EXP-05.
- Existing AC and case mappings.
- ADRs 0001–0005.

Produce a concrete technical specification without implementing it.

## 4.1 Threat model

Define:

- Assets being protected.
- Adversary assumptions.
- Local device compromise assumptions.
- Offline disk access.
- Backup theft.
- Keychain access assumptions.
- Application process compromise limitations.
- User-session and OS account boundaries.
- What encryption does not protect against.

Explicitly distinguish at-rest encryption from protection against malware or an attacker with access to an unlocked application session.

## 4.2 Data protection inventory

Produce a complete data-classification matrix covering:

- Browser catalog.
- Persistent profile SQLite databases.
- SQLite WAL.
- SQLite journals.
- Temporary database files.
- Profile metadata.
- History.
- Download metadata.
- User-created snapshots.
- Internal recovery snapshots.
- Session state.
- Recently closed tabs/windows.
- Permission grants.
- Bookmarks and saved pages.
- Backup archives.
- Recovery manifests.
- Key metadata.
- WebKit website data.
- Downloaded external files.

For each data class specify:

- Storage location.
- Sensitivity.
- Encryption requirement.
- Key scope.
- Integrity requirement.
- Backup inclusion.
- Deletion requirement.
- Private-mode behaviour.
- Remaining unknowns.

Do not claim that SQLite encryption protects WebKit's independently managed website-data store.

Do not claim that browser metadata encryption protects external downloaded files.

## 4.3 Cryptographic architecture

Specify, with justified choices:

- Encryption and authenticated-integrity construction.
- Key sizes and random generation requirements.
- Per-profile data-encryption keys.
- Key-encryption or wrapping hierarchy.
- Profile-specific key isolation.
- Nonce/IV generation and uniqueness.
- Associated authenticated data.
- Format/version identifiers.
- Authentication failure behaviour.
- Corruption detection.
- Rotation strategy.
- Key replacement and migration.
- Secure deletion limitations.

Do not invent an unverified cryptographic provider or library dependency.

Identify candidate implementations and their actual platform availability as a qualification task.

Do not write cryptographic production code.

## 4.4 SQLite protection

Specify protection for:

- Main database.
- WAL.
- Rollback journal.
- Temporary files.
- Checkpoints.
- Vacuum and migration.
- Backup snapshots.
- Crash recovery.
- File permissions and filesystem assumptions.

Define what evidence EXP-03 must capture to establish protection across all relevant database artefacts.

Do not accept a successful database-open test as proof of complete encryption coverage.

## 4.5 WebKit data protection boundary

Explicitly document:

- What the application controls.
- What WKWebsiteDataStore controls.
- Which WebKit website-data categories need protection.
- Which categories are persistent or nonpersistent.
- What can be inspected, exported, deleted or verified through supported APIs.
- What cannot be guaranteed by the application.
- How WebKit data is treated in backup and restore.
- Platform limitations and qualification requirements.

Preserve the conditional WKWebView architecture decision.

Do not assume that WebKit storage can be encrypted using the same SQLite key or mechanism.

# 5. Keychain and independent recovery specification closure

Use OD-R08, OD-R09 and OD-R19 as the owner-approved direction.

The intended custody model is:

- macOS Keychain for normal access.
- Independently held recovery material.
- Printable recovery kit.
- Exportable encrypted recovery file.
- Recovery generated locally.
- No transmission or retention of unprotected recovery secrets on Vezham servers.
- Offline recovery without a Vezham account or cloud service.

Specify the full lifecycle.

## 5.1 Key hierarchy

Define:

- Profile data-encryption key.
- Key-encryption key or wrapping layer.
- Keychain-protected representation.
- Recovery-material-protected representation.
- Recovery metadata.
- Key versioning.
- Profile identity binding.
- Key replacement and rotation.

Explain how independent recovery protects the profile key without making recovery material itself a plaintext copy of that key.

## 5.2 Recovery material

Specify:

- Printable recovery-kit format.
- Exportable encrypted recovery-file format.
- Entropy and encoding requirements.
- Confidentiality and integrity protection.
- Recovery verification.
- Copy/export confirmation.
- Loss and corruption behaviour.
- Version migration.
- Offline restoration.
- Handling of an already unlocked profile.
- Recovery when Keychain access is unavailable.

The printable format must be suitable for secure offline custody.

Do not expose recovery secrets in logs, crash reports or diagnostic output.

## 5.3 Unlock and locking lifecycle

Define:

- Normal Keychain unlock.
- Optional profile lock.
- Manual lock.
- macOS lock.
- Sleep.
- User switching.
- Inactivity lock.
- Key access invalidation.
- Key reacquisition.
- Failed authentication.
- Recovery after restart.
- Multiple profiles.
- In-flight operations.
- Download behaviour.
- Event and subscription fencing.

A UI-only lock is insufficient if the key remains available to an active data-access path.

## 5.4 Loss and failure scenarios

Define outcomes for:

- Keychain item unavailable.
- Keychain item deleted.
- Recovery material lost.
- Recovery material corrupted.
- Wrong recovery material.
- Profile database corrupted.
- Recovery manifest corrupted.
- Incompatible format version.
- Interrupted rotation.
- Partial restore.
- Existing destination conflicts.

Clearly identify the unrecoverable condition where both Keychain access and independent recovery material are unavailable.
