# Workstream A — Encryption provider and database fixtures

## A1. Candidate provenance and qualification

The current documented candidate is SQLCipher 4.20.0 with CommonCrypto.

It is a candidate, not an installed or qualified dependency.

Establish an auditable candidate record containing:

- Exact upstream project and source location.
- Exact version and immutable source revision/tag.
- Available release artifacts and checksums, where applicable.
- Build system, compiler/toolchain and supported target architectures.
- SQLite version and SQLCipher compatibility.
- Crypto-provider selection and actual build configuration.
- License and provenance review.
- Relevant upstream security advisories and known compatibility constraints.
- Whether the candidate can be built reproducibly for the project's supported macOS target.
- Any unresolved licensing, binary provenance, API or build concerns.

Do not infer that a dependency is qualified merely because it appears in a package manifest, SDK or local cache.

Do not download or execute unverified binaries.

If network access or upstream verification is unavailable, document the missing evidence and leave the qualification blocked.

## A2. Isolated provider build

Determine whether an isolated validation-only provider build can be prepared without changing product dependencies.

If feasible:

- Keep it outside production application targets.
- Pin all inputs.
- Record exact build commands and outputs.
- Record binary/source hashes and toolchain versions.
- Keep generated artifacts in a clearly identified validation-only location.
- Make the build reproducible.
- Do not add the candidate to production dependency resolution.
- Do not modify the browser's production architecture or package contracts.

If a safe isolated build cannot be prepared, produce the exact blocker and required next action instead of forcing it.

## A3. Database fixture preparation

Prepare a fixture plan and, where safely possible, isolated synthetic fixtures for:

- Catalog database.
- Profile database.
- Main database file.
- WAL.
- Journal.
- SHM.
- Temporary database artifacts.
- Independent profile key scopes.

The fixture design must follow the encryption specification.

Use synthetic records only. Do not use personal data, real browser profiles, existing user databases or original WebKit stores.

Define expected observations for:

- Correct key.
- Missing key.
- Wrong key.
- Wrong profile/scope key.
- Modified ciphertext.
- Modified authentication tag/page.
- Truncated database.
- Missing or corrupted required artifacts.
- Interrupted writes.
- Key rotation and interrupted promotion.
- Plaintext leakage detection, including a functioning positive-control fixture.

Do not claim that encryption is qualified merely because a database opens successfully.

Do not claim memory-only temporary storage without actual build/runtime evidence.

## A4. Key-binding and crypto interface review

Review the specified 32-byte per-scope key-input contract and envelope construction.

Document:

- Exact interface and ownership boundaries.
- Native key-buffer lifecycle.
- String/log exposure risks.
- Provider-specific key binding.
- Error and failure handling.
- Zeroization limitations and what can actually be demonstrated.
- AES-256-GCM/HKDF-SHA256 and CBOR format interoperability requirements.
- Scope, purpose, nonce, version and authenticated-identity validation.
- Malformed-input and bounded-parser behavior.

Do not implement a new cryptographic primitive or hand-write crypto.

Any fixture-only implementation must be clearly isolated, testable and reviewed against the canonical specification.

# Workstream B — Keychain and independent recovery qualification

## B1. Native Keychain feasibility assessment

Inspect the existing native application identity, entitlements, signing setup and Keychain integration.

Determine what can be tested using the currently authorized local environment.

Review the specified behavior for:

- Device-bound normal Keychain authority.
- Access-control policy and native user authentication.
- Cancellation and denial.
- Missing/unavailable Keychain item.
- Fresh authentication context.
- Profile/catalog scope separation.
- Key version and generation binding.
- Lock/unlock behavior.
- No secret logging or persistence in plaintext.

Do not silently change bundle identifiers, signing identities, entitlements, access groups or provisioning.

Do not sign or notarize anything as part of this task.

If native Keychain tests require a new identity, entitlement, signing permission or user action, document that prerequisite and stop before performing it.

## B2. Independent recovery fixtures

Review the proposed VXKE/VXRF and printable recovery-kit contracts.

Prepare a validation-only fixture plan, and implement isolated non-secret test vectors where possible, covering:

- Encoding and decoding.
- Canonical serialization.
- Bounded parsing.
- Version and scope validation.
- Authentication associated data.
- AEAD success/failure.
- Wrong recovery secret.
- Wrong profile/catalog identity.
- Truncated or malformed capsule.
- Modified authentication tag.
- Unsupported version or algorithm.
- Missing key version.
- Recovery-file and printable-kit interoperability.

Use synthetic keys and data only.

Never emit secrets, secret hashes or recoverable key material into logs or committed evidence.

Do not claim independent recovery qualification without verified readback, decryption, identity checks and restored synthetic records.

## B3. Offline recovery readiness

Define the minimum reproducible setup for a future independent recovery test:

- Qualified encrypted profile fixture.
- Matching recovery capsule and recovery secret.
- Independent destination environment.
- Source Keychain absence demonstrable.
- Network isolation.
- Expected synthetic records and integrity checks.
- Destination preservation and conflict behavior.
- Verification of restored scope and retained key versions.

Do not claim cross-Mac recovery if a second Mac is unavailable.

Do not substitute the source Mac or its Keychain for an independent recovery destination.

Do not execute EXP-04 while its documented prerequisites remain unmet.

- Never infer store integrity from directory presence.
- Never bypass protected container boundaries.
- Do not inspect similarly named or unrelated user data.

If a supported non-creating registry inspection cannot be performed safely, document that limitation and the exact prerequisite needed.

## C2. Per-store lifecycle observability design

Prepare an isolated validation-only design for a future new-UUID diagnostic.

It must record distinct checkpoints for each store:

1. Fixture identity and creation evidence.
2. Store and WebView ownership.
3. Navigation/service cancellation.
4. Delegate, handler, continuation and task retirement.
5. Reference-release evidence.
6. Removal invocation.
7. Callback entry.
8. Callback completion and error.
9. Registry state after completion.
10. Scoped physical-state observation.
11. Final per-store result.

Include explicit run, process, store and operation identifiers.

Do not use arbitrary sleeps as proof of deallocation, quiescence or completion.

A crash must terminate that diagnostic run and preserve all available evidence. No automatic retry or destructive cleanup.

## C3. Original evidence preservation

Do not create new UUID stores merely to work around the unresolved original-state prerequisite.

A future new-UUID diagnostic requires a separate explicit readiness decision after the original-state and environment prerequisites are understood.

# Strict authorization and safety boundaries

The following are NOT authorized by this task:

- Browser product implementation.
- Production database or crypto integration.
- Production dependency changes.
- Production UI or architecture changes.
- WebKit production lifecycle fixes.
- Signing, notarization or distribution.
- Release or deployment.
- Running EXP-03 or EXP-04 as full qualification campaigns.
- Running EXP-05, EXP-07, EXP-08 or downstream service campaigns.
- Destructive cleanup, deletion or repair of original stores.
- Recreating missing Store A.
- Modifying original fixture bytes or historical evidence.
- Resetting or replacing keys/databases.
- Changing ADR status or owner decisions.
- Claiming a PASS from documentation, compilation or partial fixture results.

Validation-only code is acceptable only where it is isolated, non-production, uses synthetic data and does not cross these boundaries.

If a task requires new signing permission, new credentials, a second Mac, destructive operations, network access to an unverified artifact or any other authorization not already established, stop at that boundary and report it.
