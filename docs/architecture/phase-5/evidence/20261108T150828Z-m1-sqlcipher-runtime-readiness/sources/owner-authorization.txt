## Step 3 – Review the encryption and key-binding contract

Trace the existing contracts across BrowserDomain, BrowserPorts, BrowserCore and BrowserPersistence.

Document:

1. Where encryption keys originate.
2. How key material reaches the SQLCipher provider.
3. How the database key is applied before any database access.
4. How key material is scoped to an individual profile.
5. How wrong-key and malformed-database failures are surfaced.
6. How key material is cleared from memory where feasible.
7. How database close and reopen operations interact with key lifecycle.
8. How WAL, journal and temporary storage are protected.
9. How private browsing remains isolated from persistent profile storage.

Identify missing or ambiguous contracts.

Do not introduce new product architecture or alter owner-approved decisions.

## Step 4 – Prepare the synthetic test matrix

Create a finite test matrix for:

### Encryption and confidentiality
- Newly created database.
- Main database file.
- WAL and SHM files.
- Rollback journal.
- Temporary database storage.
- Checkpoint and close behavior.
- Reopen using the correct key.
- Read attempt using an incorrect key.
- Plaintext detection controls.

### Key binding
- Correct profile key.
- Wrong profile key.
- Missing key.
- Malformed key input.
- Key scope mismatch.
- Repeated open/close.
- Key replacement and rotation behavior, if supported by the approved contract.

### Tamper and corruption
- Modified database bytes.
- Truncated database.
- Malformed encrypted database.
- Corrupted WAL or journal.
- Authentication/integrity failure.
- Recovery after incomplete writes.

### Interruption and recovery
- Interrupted transaction.
- Process termination during writes.
- Reopen after interruption.
- Checkpoint interruption.
- Recovery with correct key.
- Rejection with incorrect key.

For every case specify:

- Unique test identifier.
- Requirement/acceptance mapping.
- Preconditions.
- Synthetic fixture.
- Operation.
- Expected result.
- Failure oracle.
- Evidence to capture.
- Cleanup requirements.

Do not invent acceptance criteria. Map to existing requirements and identify gaps explicitly.

## Step 5 – Define evidence and security oracles

Specify how we will demonstrate:

- Persistent database encryption.
- Absence of plaintext in database sidecar files.
- Correct-key reopen.
- Wrong-key rejection.
- Profile isolation.
- Tamper detection.
- Interrupted-write recovery.
- Key lifecycle behavior.
- No unintended plaintext temporary artifacts.

Distinguish observable evidence from assumptions.

Do not claim confidentiality merely because the main database header is not readable.

Do not use production or personal browser data.
