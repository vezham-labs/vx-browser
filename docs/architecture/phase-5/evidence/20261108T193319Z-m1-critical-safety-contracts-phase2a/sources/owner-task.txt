## Primary objectives

### 1. Resolve OPEN-01: key-before-read

Investigate the pinned SQLCipher source and public API behavior.

Determine whether a supported, maintainable approach can satisfy the literal requirement that no database bytes are read before key application.

Evaluate alternatives without assuming that patching SQLite internals is acceptable.

For each alternative document:

- Exact open and key-binding sequence
- Whether any physical file read occurs before key application
- Required SQLite/SQLCipher API behavior
- Compatibility with the pinned source
- Maintenance and upgrade implications
- Security implications
- Testability and observable proof
- Failure modes

If the literal requirement cannot be met with a supported approach, state that clearly.

Do not silently weaken the requirement. Define the exact owner decision required to resolve any proposed narrower interpretation.

### 2. Resolve OPEN-02: pre-authentication write protection

Specify an enforceable design that protects existing database content before authentication.

Cover:

- Main database
- WAL
- SHM and shared-memory mappings
- Rollback journals
- Statement journals
- Temporary files
- Provider scratch files
- File replacement, truncation and deletion
- Recovery and checkpoint behavior

Define which operations are permitted before authentication and which must be denied.

Specify how the implementation proves that the original protected files remain unchanged after:

- Wrong-key authentication
- Corrupt database input
- Authenticated identity mismatch
- Interrupted open
- Process termination
- WAL or hot-journal recovery requirements

Do not treat read-only open flags or post-operation hash comparisons as sufficient enforcement.

### 3. Resolve OPEN-03: VFS and filesystem confinement

Provide a detailed architecture for:

- Descriptor-relative file access
- Stable resource identity
- Symlink and hard-link rejection
- Main database and sidecar binding
- WAL and SHM mapping behavior
- Path replacement and TOCTOU prevention
- Complete I/O observation
- Trace overflow and missing-event detection
- Temporary and unnamed file handling
- Provider direct-I/O limitations

Distinguish enforceable guarantees from observations and assumptions.

### 4. Resolve OPEN-04 and OPEN-05

Specify:

- Durable quarantine and restart reconciliation
- Process ownership and stale-child handling
- Operation identity and full UUID preservation
- IPC v2 framing and version negotiation
- Request/response state machine
- Cancellation and interrupt lifetime
- Commit outcome and receipt semantics
- Late-result fencing
- Bounded diagnostics and cleanup

Preserve the Phase 1 protocol as a separate fake conformance baseline.

### 5. Implementation readiness

Create a dependency graph identifying which contracts must be frozen before:

- Fake-provider implementation
- VFS implementation
- SQLCipher initialization
- Key binding
- First database open
- Encrypted fixture creation
- PQR runtime execution

Identify the smallest safe implementation milestone after design approval.

## Strict restrictions

This is a design-only task.

Do not:

- Implement the provider adapter
- Implement a VFS
- Launch or initialize SQLCipher
- Call `sqlite3_key` or other provider functions
- Open or create databases
- Generate encrypted fixtures
- Run encryption or PQR runtime tests
- Modify Phase 1 worker source
- Change production BrowserPersistence or BrowserCore
- Modify ADRs or owner decisions
- Change approved security requirements
- Install software or modify host configuration
- Commit or push without explicit instruction

If an issue cannot be resolved technically without an owner decision, document the precise decision required rather than making one.
