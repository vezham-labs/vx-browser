## 2. Absolute execution boundary

WS-F0 is strictly fake-only.

### Prohibited operations

Do not:

- Instantiate or invoke actual WebKit APIs.
- Create or use `WKWebView`, `WKWebsiteDataStore` or other WebKit runtime objects.
- Perform actual website-data operations.
- Initialize, link or execute SQLCipher for this milestone.
- Open, create, migrate or modify browser databases.
- Access macOS Keychain.
- Create encrypted fixtures or perform cryptographic qualification.
- Access real browser profiles or user website data.
- Perform filesystem-backed website storage operations.
- Implement production WebKit adapters.
- Implement production persistence integration.
- Change owner decisions or ADRs.
- Claim WebKit isolation, deletion, backup, recovery or security qualification.
- Claim macOS 26 runtime compatibility based on fake tests.

Use deterministic in-memory fake providers and controlled test fixtures.

If an existing test command unexpectedly invokes prohibited functionality, do not execute it. Identify and report the boundary.

### Independence requirement

The fake implementation must not depend on WebKit being installed, initialized or available.

The fake provider must be replaceable by a future WebKit adapter through explicit typed contracts.

## 3. Implementation scope

Complete all stages below in one coordinated implementation.

### F0.1 — Profile catalog and storage bindings

Implement or complete the engine-independent profile catalog and mapping contracts.

Requirements:

- Persistent profiles have stable, nonzero store identifiers.
- A profile maps to exactly one intended persistent store identity.
- Prevent accidental mapping of multiple independent profiles to the same store.
- Reject invalid, zero, duplicate or malformed identities.
- Never treat a store identifier as a capability or authorization token.
- Profile identity and website-data store identity remain separate concepts.
- Support deterministic catalog enumeration.
- Enumeration must not implicitly create missing stores.
- Missing, corrupt, duplicate or conflicting catalog entries must produce explicit states.
- Preserve unknown and ambiguous states instead of guessing.

Tests must cover valid mappings, duplicate mappings, invalid identities, missing records, corrupted records and conflicting mappings.

### F0.2 — Persistent and private scope separation

Implement explicit scope models.

Persistent scope:

- Associated with a validated persistent profile.
- Has a stable store identity.
- Supports lifecycle coordination through the provider contract.

Private scope:

- Has an ephemeral session identity.
- Must never be assigned a persistent store identity.
- Must never appear in the persistent profile catalog.
- Must not produce persistent website-data records.
- Must not be restored as a persistent session after process restart.

Enforce scope isolation through types and validation, not only naming conventions.

Test attempts to cross persistent/private boundaries.

### F0.3 — Construction policy and default-store prevention

Implement a fake construction-policy layer.

Requirements:

- A persistent scope requires explicit validated store resolution.
- A private scope requires explicit ephemeral-store resolution.
- Construction must fail if resolution is absent, invalid or ambiguous.
- Never silently fall back to a default store.
- Store resolution must happen before the abstract web-view construction request.
- No implicit getter or factory may create a default store.
- The construction policy must not expose native capabilities to callers.

Use a fake construction recorder to verify call ordering.

Test missing assignment, invalid identity, failed resolution, default-store fallback attempts and incorrect construction order.

### F0.4 — Lifecycle coordinator

Implement a deterministic lifecycle state machine for website-data scopes.

Cover the supported lifecycle operations:

- Register
- Resolve
- Activate
- Quiesce
- Retire
- Switch
- Reconcile
- Fail
- Quarantine

Requirements:

- State transitions must be explicit and validated.
- Illegal transitions must fail deterministically.
- Concurrent or repeated lifecycle requests must not produce inconsistent states.
- A scope cannot be retired while dependent fake resources remain active.
- A scope cannot be activated while quarantined.
- A failed operation must not be reported as successful.
- Switching profiles must not transfer authority or website data between scopes.
- All operations must produce bounded, sanitized diagnostic events.

Use deterministic fake resource references and lifecycle participants.

### F0.5 — Deletion state machine

Keep these operations distinct:

1. Clear selected website data.
2. Remove an entire persistent website-data store.

Requirements:

- Clearing selected data must not implicitly remove the store.
- Store removal must require an explicit retirement and dependency check.
- Active references must block removal.
- Partial, failed and uncertain outcomes must remain distinguishable.
- A failed removal must never be reported as successful deletion.
- Retrying an operation must be idempotent where the contract allows.
- Unknown deletion results must not be interpreted as success.
- Do not claim secure erasure or physical data destruction.

Use fake deletion providers with configurable success, partial completion, failure and unknown outcomes.

### F0.6 — Recovery and restart reconciliation

Implement engine-independent recovery coordination.

Requirements:

- Reconcile catalog entries against fake provider observations.
- Distinguish missing, available, conflicting and unknown stores.
- Preserve evidence of uncertain or interrupted operations.
- Quarantine unsafe or ambiguous scopes.
- Never silently recreate a missing store to make recovery appear successful.
- Never activate a quarantined scope.
- Preserve private-session non-persistence.
- Recovery must not replay website requests, form submissions or POST operations.
- A restart must not convert an incomplete deletion into a successful deletion.
- Recovery outcomes must be deterministic and auditable.

Use controlled fake restart snapshots and provider state.

### F0.7 — Failure injection and diagnostics

Build deterministic failure injection into the fake provider infrastructure.

Cover:

- Provider unavailable.
- Store missing.
- Invalid store identity.
- Duplicate identity.
- Conflicting catalog mapping.
- Construction failure.
- Activation failure.
- Quiescence timeout.
- Outstanding references.
- Partial deletion.
- Unknown deletion result.
- Removal failure.
- Restart interruption.
- Corrupt recovery metadata.
- Quarantine persistence failure.
- Reconciliation mismatch.

Diagnostics must:

- Be bounded.
- Be sanitized.
- Avoid full URLs and website content.
- Avoid secrets and key material.
- Avoid exposing native paths or capabilities.
- Include stable operation and failure classifications.
- Preserve enough information to understand test failures.

Do not invent production logging guarantees from fake diagnostics.

### F0.8 — Integration scenarios

Create end-to-end fake-only scenarios covering:

1. Create and activate a persistent profile.
2. Switch between two persistent profiles.
3. Open and close a private scope.
4. Verify private data does not enter the persistent catalog.
5. Reject default-store fallback.
6. Reject cross-profile store access.
7. Clear selected website data.
8. Retire and remove a persistent store.
9. Block removal while resources remain active.
10. Recover after interrupted lifecycle operations.
11. Quarantine an ambiguous store.
12. Reconcile after simulated process restart.
13. Reject activation of a quarantined scope.
14. Verify failed and uncertain deletions remain unresolved.

Test both successful and adversarial paths.

### F0.9 — WKS qualification and traceability

Use the existing 40 proposed WKS cases as the authoritative qualification inventory.

For each WKS case:

- Identify whether WS-F0 can test it using fake infrastructure.
- Map it to implementation contracts and test cases.
- Record actual execution status.
- Record exact test command and result.
- Record limitations and remaining runtime dependencies.

Use honest statuses such as:

- `PASS_FAKE_ONLY`
- `FAIL`
- `BLOCKED`
- `NOT_APPLICABLE`
- `NOT_RUN`

Do not mark a case as fully qualified if it requires actual WebKit, macOS runtime behavior, Keychain, filesystem semantics or other prohibited operations.

Keep fake-only evidence clearly distinguishable from runtime evidence.

Preserve all 50 original SQLCipher PQR definitions and historical results without modification.

Do not mark SQLCipher PQR cases as passed through this implementation.

## 4. Engineering expectations

Follow the repository's existing architecture and language conventions.

Prefer:

- Explicit typed contracts.
- Small, cohesive modules.
- Deterministic state machines.
- Dependency injection.
- Protocol-based fake providers.
- Immutable identifiers.
- Explicit error types.
- Idempotent operations where appropriate.
- Testable orchestration independent of native frameworks.

Avoid:

- Global mutable state.
- Hidden default behavior.
- Implicit resource creation.
- Boolean-heavy APIs that obscure lifecycle state.
- Broad catch-all error handling.
- Silent recovery.
- Production abstractions that cannot be tested independently.
- Unnecessary new dependencies.
- Duplicate implementations of existing contracts.

Do not create speculative abstractions solely for future WebKit functionality.

If a contract requires clarification, preserve the ambiguity and document it.
