Execute all WS-F2 stages in one coordinated Codex run. Use internal stages and acceptance gates to maintain correctness. Do not ask the product owner to approve routine implementation decisions between stages.

# 3. Product and architecture boundaries

These boundaries are mandatory throughout WS-F2.

## 3.1 WebKit owns website storage

WebKit remains authoritative for:

- Cookies.
- localStorage.
- IndexedDB.
- HTTP cache.
- Service workers.
- Website-data formats and internal paths.

Continue using public WebKit APIs.

Never:

- Parse or manipulate WebKit internal storage databases.
- Put WebKit-owned files inside the Vezham SQLCipher database.
- Wrap WebKit-owned files in SQLCipher.
- Invent a WebKit storage path or schema.
- Claim secure physical erasure.
- Depend on undocumented/private WebKit APIs.

## 3.2 BrowserCore owns browser policy and lifecycle

BrowserCore owns:

- Profile identity and state.
- Persistent and private session intent.
- Session lifecycle.
- Profile locking policy.
- Permission policy.
- Storage operation intent.
- Resource lifecycle coordination.
- Recovery and reconciliation.
- Browser-owned metadata lifecycle.

BrowserCore must remain engine-independent.

## 3.3 BrowserPorts owns contracts

BrowserPorts defines typed, engine-independent contracts for BrowserCore.

Do not expose:

- `WKWebView`
- `WKWebsiteDataStore`
- Keychain implementation objects
- SQLCipher connections
- Native AppKit types

through BrowserDomain or BrowserCore.

## 3.4 BrowserPersistence owns Vezham data

Vezham-owned persistence includes:

- Profile catalog.
- Stable profile identity.
- WebKit store UUID mappings.
- Descriptor versions.
- Lifecycle journals.
- Tombstones.
- History.
- Bookmarks.
- Preferences.
- Session descriptors.
- Permission grants.
- Download metadata.
- Approved user-created archives.
- Backup manifests and restore metadata.

Do not place website content or WebKit-owned internal storage in this database.

## 3.5 Native host owns native objects

The AppKit application and native adapters own:

- WebKit objects.
- Native lifecycle registries.
- Keychain operations.
- SQLCipher connection construction.
- Native resource references.
- Main-thread and actor-isolation requirements.

Keep implementation-specific types behind appropriate adapters.

## 3.6 No mandatory cloud dependency

Local browser operation must not require:

- A Vezham account.
- Cloud synchronization.
- A remote server.
- A local browser service process.
- Tamizhi autonomous actions.

Do not introduce these as part of WS-F2.

# 4. Mandatory security decisions and restrictions

## 4.1 D2A-01 remains unresolved

D2A-01 is still Proposed/Not Decided.

The existing SQLCipher pre-key safety issue must not be bypassed.

In particular, do not silently introduce a pre-key database-header read, application/VFS read exception, hashing/copy exception or other workaround.

Do not:

- Weaken the existing pre-key data-read restriction.
- Change the approved SQLCipher source pin.
- Change the vendor-signature verification record.
- Claim runtime encryption qualification based only on source authenticity or build success.
- Treat a successful database open as authorization to alter the unresolved decision.

### Required handling

Investigate whether the actual protected catalog can be implemented using an already approved, compliant database-initialization path.

If the unresolved D2A-01 decision prevents opening an existing encrypted database safely:

1. Preserve the safe behavior.
2. Do not implement an unauthorized workaround.
3. Implement and test independent catalog contracts and non-conflicting integration components.
4. Document the exact blocked operation.
5. Record the specific technical and security trade-off.
6. Prepare a separate owner-decision proposal if needed.
7. Continue all independent WS-F2 work.

Do not mark the protected catalog fully integrated or runtime-qualified if its real database initialization remains blocked.

A new ADR or decision proposal must not automatically change an existing owner decision.

## 4.2 Keychain security

Use macOS Keychain for Vezham-owned secrets and keys.

Do not store keys in:

- Source code.
- Configuration files.
- Environment variables as a persistent substitute.
- Logs.
- Browser preferences.
- Profile descriptors.
- SQLite metadata.
- Backup manifests.

Define explicit Keychain access, accessibility, lifecycle and recovery behavior.

Do not claim stronger protection than the actual Keychain configuration and tested behavior establish.

## 4.3 Private-session privacy

Private sessions must remain memory-only at the Vezham browser-metadata level and use WebKit nonpersistent stores.

Never persist private:

- History.
- Session restoration state.
- Snapshots.
- Website-data-store mappings.
- Private page contents.

Do not promise protection against OS swap, crash reports, process memory inspection or forensic artifacts.

## 4.4 Fail-closed behavior

If a profile's identity, key, catalog state, permission or storage association is uncertain:

- Do not silently fall back.
- Do not publish an incompletely initialized profile.
- Do not expose another profile's resources.
- Do not silently create a replacement profile.
- Do not claim a destructive operation succeeded without evidence.

# 5. Stage A — WebKit runtime hardening

Start with the actual WS-F1 native implementation.

Do not reimplement it from scratch.

## A1. Resolve WS-F1 HTTP-cache inconclusive results

WS-F1 recorded HTTP-cache persistence as inconclusive for both tested profiles.

Investigate the actual behavior using controlled synthetic test origins.

Test:

- Cache population.
- Cache reuse within one profile.
- Cache isolation between profiles.
- Cache behavior after web-view reconstruction.
- Cache behavior after normal application restart.
- Cache behavior after abrupt termination.
- Cache behavior after selected website-data clearing.
- Cache behavior after full clearing.
- Cache behavior after store removal.

Distinguish:

- Browser-visible HTTP caching behavior.
- WebKit-managed disk persistence.
- HTTP response semantics.
- Cache revalidation.
- Network retrieval.
- Other WebKit optimizations.

Do not infer disk persistence merely from a page rendering without an observed network request.

Use controlled responses, explicit cache headers, unique fixture identifiers and server-side request observations.

Report the exact behavior observed.

If WebKit does not expose sufficient observability to prove a particular property, retain an INCONCLUSIVE disposition and explain why.

Do not modify WebKit internals to obtain evidence.

## A2. Resource lifecycle

Expand native qualification for:

- Multiple web views per profile.
- Multiple windows.
- Profile switching.
- Web-view close.
- Window close.
- Profile close.
- Application termination.
- Outstanding navigation.
- In-flight clear operations.
- In-flight store-removal operations.
- Resource release and re-registration.

Preserve WS-F1's observed 15-second private-retirement deadline as an evidence-backed qualification parameter, not an unconditional platform guarantee.

Retain the earlier two-second failures.

If you change the deadline or implementation, document why and preserve the original evidence.

## A3. Store assignment and publication fencing

Verify again:

- Persistent profile UUID resolution.
- Private nonpersistent store resolution.
- Explicit store assignment before web-view construction.
- No default-store fallback.
- No navigation before storage assignment.
- No publication of uncertain resources.
- Correct profile identity association.

Ensure new catalog and locking integration does not weaken these rules.

## A4. Clear and remove behavior

Continue to distinguish selected website-data clearing from entire store removal.

Qualify:

- Selected data categories.
- Selected origins where supported.
- Full selected-profile clearing.
- Interrupted clearing.
- Partial clearing.
- Store removal with outstanding resources.
- Store removal callback failure or uncertainty.
- Restart reconciliation after incomplete operations.

Never promise physical or forensic erasure.

### Stage A gate

- HTTP-cache result resolved or explicitly inconclusive with evidence.
- Existing WS-F1 behavior preserved.
- No default-store fallback.
- Native lifecycle tests expanded.
- Clear/remove semantics preserved.
- Fake and native outcomes reported separately.

# 6. Stage B — Actual protected Vezham profile catalog

Implement the real Vezham-owned profile catalog using the repository's established BrowserPersistence architecture.

Do not create a second competing catalog.

## B1. Catalog responsibilities

The catalog should represent:

- Stable Vezham profile identity.
- Human-readable profile metadata.
- Profile type.
- Persistent profile state.
- WebKit store UUID mapping.
- Descriptor version.
- Creation state.
- Publication state.
- Lock state.
- Retirement state.
- Tombstone state.
- Migration state.
- Relevant lifecycle timestamps.
- Operation identifiers needed for idempotency and reconciliation.

Keep private-session identities out of persistent profile-store mappings.

## B2. Persistence implementation

Inspect the existing SQLCipher and persistence infrastructure.

Use the approved pinned SQLCipher source and existing build configuration.

Implement:

- Schema and migrations.
- Typed repository operations.
- Transaction boundaries.
- Catalog creation and lookup.
- Descriptor serialization.
- Catalog update and deletion.
- Tombstone persistence.
- Recovery journal.
- Idempotent lifecycle operations.
- Corrupt or unsupported descriptor handling.
- Safe error propagation.

Do not introduce a new database engine or replace SQLCipher without an explicit owner decision.

Do not mix native WebKit website data with Vezham catalog records.

## B3. Catalog lifecycle consistency

The catalog must be consistent with the native lifecycle.

Consider:

- Catalog creation before native store creation.
- Native store creation before catalog finalization.
- Catalog publication.
- Failed web-view construction.
- Profile deletion.
- Interrupted store removal.
- Restart reconciliation.
- Missing native stores.
- Missing catalog records.
- Duplicate operation requests.

Use explicit operation states and idempotency.

Do not claim a cross-system atomic transaction between SQLite and WebKit.

Model the lifecycle as a recoverable operation with observable state and compensation/reconciliation.

## B4. Schema migration

Provide:

- Explicit schema version.
- Ordered migrations.
- Migration transaction rules.
- Migration failure behavior.
- Corrupt catalog behavior.
- Unsupported future schema behavior.
- Restart during migration behavior.
- Recovery and verification.

Do not silently downgrade or discard catalog information.

### Stage B gate

The actual catalog integration is complete only if:

- The native application uses it.
- Persistent profile records survive process restart.
- Migrations run safely.
- Lifecycle operations update it correctly.
- Recovery reads actual persisted state.
- Failure behavior is tested.
- Key and SQLCipher boundaries remain intact.

If D2A-01 blocks actual database initialization, mark the affected integration as BLOCKED and continue other work. Do not substitute an unprotected database and call it protected.

# 8. Stage D — Profile locking and lifecycle security

Implement profile locking as a real browser lifecycle policy, not merely a UI state.

## D1. Define lock semantics

Establish explicit states such as:

- Unlocked.
- Lock requested.
- Quiescing.
- Locked.
- Unlock requested.
- Unlocking.
- Recovery required.
- Failed/uncertain.

Use the existing state-machine conventions where possible.

## D2. Lock behavior

When locking a profile:

1. Fence new navigation and web-view construction.
2. Prevent new operations from acquiring the profile.
3. Apply the defined behavior to existing windows and web views.
4. Quiesce or retire active resources according to the approved policy.
5. Handle in-flight downloads and operations explicitly.
6. Ensure profile-owned persistence operations cannot bypass the lock.
7. Establish a clear final locked state.

Do not claim that a profile is locked while active resources can continue using it contrary to the defined policy.

Do not assume hiding a window or showing a lock screen is sufficient.

## D3. Unlock behavior

Unlock must:

- Validate the required authorization.
- Resolve the profile's actual identity.
- Validate key availability where required.
- Reconcile pending lifecycle operations.
- Reconstruct resources safely.
- Avoid automatic navigation replay of unsafe requests.
- Publish only after required checks succeed.

Do not silently unlock on an ambiguous or failed authorization result.

## D4. Multi-window and concurrency

Test:

- One profile across multiple windows.
- Multiple profiles open simultaneously.
- Lock during navigation.
- Lock during clear.
- Lock during download.
- Concurrent lock requests.
- Unlock while recovery is pending.
- Application termination during locking.
- Restart while a profile is locked.

Ensure the lock state is profile-specific.

One profile's lock must not accidentally unlock, close or expose another profile.

### Stage D gate

- Real lock/unlock implementation.
- Lifecycle fencing enforced by the native application.
- Concurrent operations safely handled.
- Recovery behavior defined and tested.
- No false locked-state claims.

# 10. Stage F — Backup, restore and deletion

Establish accurate backup and restore behavior for Vezham-owned browser data.

Do not promise complete portable backups of WebKit-managed website storage.

## F1. Define backup scope

Classify every data category:

1. Vezham-owned profile metadata.
2. Vezham-owned history.
3. Bookmarks.
4. Preferences.
5. Session descriptors.
6. Permission grants.
7. Download metadata.
8. User-created archives/snapshots.
9. WebKit-owned website data.
10. Actual downloaded files.
11. Private-session data.
12. Internal recovery journals.

For each category, document:

- Backup included/excluded.
- Encryption.
- Profile scope.
- Retention.
- Deletion semantics.
- Restore behavior.
- Portability limitations.

Preserve OP-01 through OP-04 and OD-R01–OD-R20.

Do not silently change their meaning.

## F2. Backup implementation

Implement backup for approved Vezham-owned categories.

Requirements:

- Explicit backup manifest.
- Versioned format.
- Profile identity.
- Schema version.
- Integrity validation.
- Encryption where required.
- Safe output handling.
- Atomic finalization where supported.
- Incomplete backup detection.
- Recovery after interrupted backup.

Do not include Keychain secrets or raw encryption keys in a backup archive.

If a supported recovery design requires a recovery mechanism, implement only an approved one. Otherwise document the limitation.

## F3. Restore implementation

Restore must validate:

- Manifest version.
- Data integrity.
- Profile identity.
- Schema compatibility.
- Key availability.
- Data-category compatibility.
- Conflicting profile state.
- Existing catalog records.
- Tombstones and deletion state.

Restore must not:

- Recreate private sessions.
- Restore private browsing history.
- Replay forms or POST requests.
- Silently overwrite a different profile.
- Reintroduce previously deleted data.
- Restore unsupported WebKit internal files.

## F4. Deletion semantics

Preserve the established owner policies.

In particular:

- History deletion must be respected by backup and restore.
- Download metadata deletion does not automatically delete the actual file.
- User-created snapshots remain separate from internal recovery snapshots.
- Private data must not enter persistent backup.
- Deletion must not silently reintroduce records during recovery.

Qualify individual deletion, bulk deletion and deletion followed by restore.

## F5. WebKit data and backup boundary

WebKit-managed website storage remains outside the Vezham catalog backup.

Do not invent a portable WebKit backup implementation.

If WebKit public APIs support an approved export capability, evaluate it separately and document exactly what it covers.

Do not infer complete website-data backup from localStorage-only or other partial export behavior.

### Stage F gate

- Backup and restore of approved Vezham-owned data implemented.
- Manifest versioned and validated.
- Deletion semantics preserved.
- Private data excluded.
- WebKit storage limitations explicit.
- Interrupted backup/restore tested.

Execute the complete WS-F2 milestone in one coordinated Codex run.

Do not pause for routine owner decisions.

You may make normal implementation decisions that are consistent with the established architecture and approved owner decisions.

If a new security or product decision is genuinely required:

1. Preserve the safest behavior.
2. Continue independent implementation work.
3. Document the unresolved question.

5. Prepare a separate decision proposal.

- Add cloud synchronization.

- Add autonomous Tamizhi browser actions.
- Introduce extensions or dynamic plugins.

- Rewrite historical evidence.
- Modify unrelated repositories or applications.
