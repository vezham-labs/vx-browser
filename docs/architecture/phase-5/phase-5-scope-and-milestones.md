# Phase 5 scope and milestones

**Date:** 2026-11-07. **Status:** prepared and reviewed plan; **M0 foundation Passed within its bounded scope; M1 design prepared for owner review; M1 implementation and M2-M8 are Planned / Not Started**. Criteria describe required outcomes, not passes. Phase 4.2 was documentation only; current M0 evidence is recorded separately in [reports](reports/README.md) and [run locations](evidence/README.md).

The current [M1 design packet](reports/M1/README.md) is a design-only submilestone. Its proposed ADRs, schema and contracts do not pass the M1 implementation criteria below. Owner review and separate implementation authorization remain required.

## Approved direction and scope

Use the [owner approval record](../phase-3/owner-approval-decision.md) and [approved boundary baseline](../phase-3/browser-mvp-architecture-baseline.md): Phase 3 closure APPROVED; WKWebView CONDITIONAL ACCEPTANCE for MVP planning and implementation; architecture baseline APPROVED. The conditional choice does not establish unconditional production-engine or release readiness. ADR 0001 remains Proposed after consistency correction; it does not revoke the already given conditional direction.

In scope for later authorized implementation: native foundation, an engine-independent browser core/local state, one WKWebView adapter, React/TypeScript/HeroUI v3 chrome, validated trust boundaries, profiles/private sessions, native permission/file services, local-first compatibility/reliability and internal release engineering. Core runtime/storage/transport and release technology choices are still explicit design tasks, not silently selected by baseline approval.

Excluded: Aura, Chromium/CEF implementation, public distribution and production Tamizhi. Optional Vezham identity/cloud is outside the required foundation and cannot be required to browse. The plan does not authorize even an optional account/sync feature implementation without its own scope. Phase 3 source/evidence/manifests/archives stay immutable references.

M0 → M1 → M2 → M3 → M4 → M5 → M6. M3's trust-boundary slice must be verified before privileged UI commands are exposed; static UI design may be prepared in parallel but may not bypass the dispatcher. M5 backend service design can overlap M3/M4, while integrated privacy/permission/file acceptance waits for all dependencies. M7 release design can begin after M0 and develop alongside M6 once dependencies stabilize. M8 depends on completed implementation and resolved release-critical conditions; minimum-OS runtime/signing/notarization stay at this final stage.

## Risks and stop/exit conditions

| Risk/dependency                                                                              | Required disposition                                                                                                                                                                                                |
| -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Unresolved core runtime, local store, UI origin/transport, permissions or transfer semantics | Resolve/document the choice before its dependent work package; do not replace approved boundaries with convenience coupling.                                                                                        |
| Account/MFA/SSO/passkey/edit/payment/conference compatibility unknown                        | Name launch-critical subflows and approved environments. Keep current public-only/account/media restrictions; do not repeatedly retry without access or new information.                                            |
| Profile/private leak, page-to-native privilege escalation or unauthorized file/device access | Stop affected milestone and release; remediate and produce scoped evidence. Conditional acceptance cannot waive a hard defect.                                                                                      |
| Broader stale/disposal/in-flight recovery and file lifetime behavior unknown                 | Add finite implementation-revision cases at M5/M6; no reopening endless Phase 3 prototype loops.                                                                                                                    |
| OS-driven engine changes and unqualified current performance                                 | Assign platform/security response ownership and qualify exact future revisions; no inherited benchmark pass.                                                                                                        |
| Installer/updater/key custody/rollout choices or release access unavailable                  | Design/prepare under M7, keep actual release checks blocked/deferred until prerequisites exist, and do not distribute.                                                                                              |
| ADR lifecycle remains Proposed                                                               | Keep formal status unchanged pending an explicit status disposition. Use the recorded conditional decisions as authority within scope; do not demand their reapproval or infer unconditional production acceptance. |

Each future milestone exits only when its declared criteria have evidence or an explicit allowed partial/blocked disposition. A blocked external workflow may allow unrelated development to continue; it does not complete compatibility or release. A failed verification may be retried only after a recorded code/environment/method change or a justified new diagnostic question. Phase 3 closure stays approved regardless of new Phase 5 work; new defects belong to their own revision record.

Phase 5 overall exit means an implemented, internally release-eligible MVP with accepted evidence for all applicable mandatory gates and a separate release-owner decision. Until then it is incomplete/conditional; no complete browser readiness, public distribution or unconditional engine acceptance is inferred.
