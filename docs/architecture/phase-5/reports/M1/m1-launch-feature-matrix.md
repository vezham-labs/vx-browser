## Meaning of classification and timing

- **Required for first MVP:** missing minimum behavior leaves its requirement unmet. Implementing it in M2-M8 still makes it required for the first MVP; a later implementation milestone does not mean deferred beyond MVP.
- **Optional for first MVP:** may be omitted without removing another required outcome; if included, all applicable security/privacy/access gates still apply.
- **Deferred to later milestone:** recommended outside the required first-MVP foundation, with separate product/implementation/access scope before activation. Architectural optionality does not itself authorize the feature.
- **Not in scope:** established exclusions remain. This packet does not reopen them.

A built-in module can be structurally optional yet implement a required launch feature. Provider registration/readiness is not authorization or feature acceptance. M0 supplies a bounded native Ready window, not the tabs/engine/core/security implementation described here.

## Required recovery and optional automatic reopening

[Ledger:D14](../../../phase-3/browser-acceptance-gate-ledger.md) explicitly requires durable recovery/session history and private-state exclusion across host crash/restart. LF13 therefore remains Required. Recommended minimum is an available, opt-in durable snapshot/explicit restore path; the owner must decide exact capture/UX policy before implementation. Default-off automatic reopening (LF15) is compatible with that minimum; classifying all session recovery Optional would weaken an existing gate and is not proposed.

Test content-process recovery, host-crash/restart recovery, ordinary per-view back/forward history and opt-in/opt-out/private exclusions separately. No previous prototype suite transfers acceptance to the new core, and no user privacy choice is overridden to satisfy a test.

## Open scope and access questions

OD17 must name the launch-critical subflows, supported permission kinds and required native operations. The representative Google Workspace/Microsoft365/GitHub/Figma/Notion/payment/conferencing/Vezham workflows are not replaced by landing-page visits. Public-pages-only and separate account/media authorization restrictions remain. Any required subflow without evidence stays Blocked for compatibility/release; this does not prevent a separately approved fake core/store proof.

Search means a Browser feature here: address-bar/web-query provider or advanced local full-text search, not a target website's own search function. A website workflow's required search still belongs to that compatibility test. No search provider, credential/cloud endpoint, cross-profile query or sync feature is selected by this matrix.

Permission enforcement never becomes optional. When a permission UX/provider is absent, the mandatory native route returns deny/cancel; that safe fallback does not pass a required grant/revoke workflow. Grant types without a documented supported callback remain unsupported, not guessed into allow. Tamizhi/services/extension timing must not introduce a startup or local-state dependency.
