# M1 Persistent-Profile Encryption Specification

Version 1.0 — Proposed technical contract, 2026-11-08. Implements existing SPEC-04 and the protection portions of SPEC-03/05/07/08/12; maps REQ-05/06/07/08/14/19/22 and AC05/06/07/08/12/14/15. Owner authority: OD-R07/08/09/18/19 and existing OP policies, not a new owner decision. Product encryption implementation and release are Not Authorized.

## 1. Closure boundary and sources

This document closes the normative cryptographic choices, key scopes, protected-data inventory and required failure behavior sufficiently to prepare qualification fixtures. It does not qualify a provider, validate a format, establish secure memory erasure or pass an experiment. [Key/recovery specification](m1-keychain-and-independent-recovery-specification.md) defines the exact bootstrap and custody protocol. [Readiness](m1-validation-readiness-remediation.md) identifies remaining executable prerequisites.

## 2. Threat model

Protect browser-owned persistent content against offline theft/copying of profile databases, backups, snapshots and local metadata when encryption keys/recovery secrets are unavailable. Detect modified ciphertext and wrong key/profile/format before accepting data. Prevent key reuse across profiles and unauthorized data delivery across normal application boundaries.

Assume the supported OS, CSPRNG, platform cryptographic implementations and Keychain access controls behave as qualified. File ownership/permissions and App Sandbox are required in addition to encryption. FileVault is a useful OS-layer protection, not a substitute for application encryption; its actual configuration is not established by this remediation.

An attacker controlling the unlocked trusted application process, its injected code, OS kernel, authenticated OS account or recovery secret may read active plaintext/keys or authorize operations. Same-process Core/Host is not a memory security boundary. Encryption does not prevent screenshots, keylogging, malicious page content, all traffic metadata, live authorized queries, denial of service, storage-size/timing leakage or tampering followed by destructive file deletion.

Application-level profile locking must actually revoke active data-access paths; it does not turn the running process into a hardware enclave. Independent recovery material is another decryption authority. Old ciphertext plus its old valid keys remains recoverable; neither key rotation nor SSD deletion guarantees erasure of all historical copies.

## 4. Cryptographic construction and provider qualification

### Database suite

Qualification candidate: official SQLCipher 4.20.0 Community/CommonCrypto Apple build, or a documented vendor-equivalent build with the identical qualified format. It is not installed, approved as a dependency or runtime-qualified here. Candidate source/binary digest, build recipe, SQLite baseline, full license/provenance and vulnerability review must be fixed before EXP-03. No fallback to stock sqlite3 or a made-up encryption shim.

Normative candidate configuration:4096-byte encrypted pages; AES-256-CBC with per-page HMAC-SHA512 enabled; provider-generated random page IVs; SQLCipher 4 compatibility; no plaintext database header; PBKDF2-HMAC-SHA512 with 256,000 iterations provider key derivation. Supply 32 bytes of uniformly random profile key material through a reviewed length-explicit C binding, treated as binary passphrase input to this suite. Do not silently confuse that with SQLCipher hex/raw-key syntax or log/interpolate key PRAGMAs. Documented provider behavior is a candidate, not evidence for this app. [Design](https://www.zetetic.net/sqlcipher/design/), [API](https://www.zetetic.net/sqlcipher/sqlcipher-api/).

Provider internals own page-IV/MAC-subkey derivation. Application code must not reimplement CBC, page MACs or encryption pager hooks. Profile identity, key version and minimum reader/writer version are validated after authenticated open. A valid old database can still be replayed: page authentication is not whole-file freshness or deletion reconciliation.

### Envelopes, managed blobs and archives

Use Apple CryptoKit AES-256-GCM,128-bit tag,96-bit nonce,32-byte keys. Derive purpose/scope-specific wrapping keys with HKDF-SHA256 and32-byte random salt; never use a profile DEK directly as both database and wrapping key. These choices use existing platform APIs whose declarations are present in the installed SDK; runtime behavior and macOS 26 remain unqualified. [Apple GCM](https://developer.apple.com/documentation/cryptokit/aes/gcm), [HKDF](https://www.rfc-editor.org/rfc/rfc5869).

Every new encryption/rewrap operation uses a fresh 256-bit salt and 96-bit nonce and a monotonically advancing authenticated wrapping generation. Byte-copying an unchanged authenticated recovery slot during a normal-KEK-only rewrite is not a new encryption operation. No key/nonce pair may repeat. The writer must reject a duplicate record tuple and RNG failure; retries use fresh salt/nonce. A new archive gets a new archive key/UUID; never resume/rewrite a partially emitted archive under reused nonces. For chunked payloads, derive per-archive content key; nonce =32-bit per-archive prefix +64-bit big-endian unique chunk index. Index0 authenticates the manifest,1..N payload chunks; cap N at2^32−1 and stop rather than wrap. Bind archive UUID, format/suite/scope/key generation, chunk index, total count, exact length and content type in AAD. Final manifest authenticates selection and ordered content digests. This specifies crypto framing; coherent multi-resource snapshot/restore protocol remains SPEC-12 work.

AAD is deterministic CBOR with fixed integer-key schema; UUIDs are16-byte values, counters unsigned integers, no duplicate/unknown critical fields, no indefinite lengths, no noncanonical encoding. Scope/version/purpose/slot/generation must match native expectations, not untrusted path claims. Salt/nonce/security-relevant slot-header fields are authenticated. The exact §2 key specification separates independently authenticated slots from advisory container-write metadata; outer hints never supply authority or freshness alone. No URLs, filenames or secrets in outer headers. Reject malformed/unknown format before expensive work. Envelope ≤1MiB,≤64 key-version entries, parser depth≤8; size extensions require new reviewed format version, not permissive decoding. CBOR is a format choice, not a new installed library. [RFC8949](https://www.rfc-editor.org/rfc/rfc8949).

Authentication failure returns a coarse unavailable/corrupt-key-or-data result, publishes no plaintext, preserves source bytes and never creates replacement keys over ciphertext. Hashes alone are not authentication. Verify complete archive/manifest/selected resources before promotion; validated chunks alone cannot authorize partial destructive publication.

## 5. SQLite artifact and I/O contract

- Main/catalog/profile opens must identify the qualified library, crypto provider/configuration and expected key/schema identity before normal access. Existing files must not use CREATE/reset fallback on wrong/missing keys.
- Force SQLITE_TEMP_STORE=3 at candidate build and require memory temp policy at connection configuration. Refuse a binary that cannot prove the required compile settings. This concerns temporary tables/indices, not permission to ignore WAL/journal/SHM artifacts. No large query may silently spill plaintext; memory pressure returns bounded failure. [SQLite options](https://www.sqlite.org/compile.html#temp_store).
- Normal profile workload uses WAL with synchronous FULL and foreign-key enforcement as the proposed qualification configuration. EXP-03 must inspect returned settings and actual artifacts, not assume unsupported PRAGMAs fail loudly.
- Capture WAL frames, rollback journal, statement journal, SHM, vacuum/rebuild and migration paths separately on disposable copies. Distinguish encrypted page payload from headers/path/size metadata. A marker scan is only a detector control, never encryption proof. Review provider documentation/build and corruption/incorrect-key behavior.
- Checkpoint/close must complete on the owned serialized worker. Do not manually erase WAL/journal files to force recovery. Outstanding transactions/statements/cursors and encrypted key buffers must retire before lock completion.
- Vacuum/migration/rekey operates only on reviewed protected resources. Use quiesced encrypted copy-and-promote for DEK replacement; do not rely on unqualified in-place rekey atomicity. Retain original encrypted resources and both required key versions until destination integrity/reopen/recovery verification and durable promotion complete.
- Use a coherent database snapshot interface whose encryption output is qualified for this exact provider. Neither copying a live main DB alone nor the SQLite backup API's name proves encrypted output. Do not create a plaintext staging database to encrypt later.
- No cross-profile ATTACH or multi-database master-journal transaction in the initial adapter. Catalog/profile/native resources use explicit checkpointed reconciliation, not an implied global SQL transaction.
- Restrict diagnostic/SQL tracing; never expand bound full URLs/keys/queries into logs. Record opaque IDs, booleans, sizes and artifact hashes. Ordinary SHA256 checksums do not authorize restoring stale data.
- State disk-full/busy/I/O/authentication errors and committed receipts truthfully. Interrupted migration preserves originals and denies unknown/newer schemas.

EXP-03 must retain exact build/source/provider/configuration, keys represented only by test identifiers, main/WAL/journal/SHM/temp inventories, positive plaintext-detection controls, correct/wrong/missing key outcomes, tamper/truncation/page-swap controls, checkpoint/vacuum/snapshot/rotation/fault/reopen observations, settings and scope-qualified review. Passing open/read is insufficient. No such execution occurred in remediation.

## 6. Rotation, deletion and OS limitations

Wrapping-key rotation changes authenticated key slots; DEK rotation uses encrypted copy-and-promote. Current and older key-version dependencies must be explicit. A retained manual snapshot/backup may still need an older DEK; never destroy that key silently. Failed promotion retains a recoverable prior state and an authenticated operation intent; restarting cannot guess which sole source to discard.

Deleting current records invalidates derived state and tracked snapshots/recovery projections according to existing deletion policy. Independent deletion records filter known stale restores; unknown coverage requires explicit bound confirmation. An old disconnected archive cannot know later deletion decisions. No cryptographic-erasure promise covers copied keys, printed kits, external archives, OS snapshots, SSD remapping or a compromised running process.

## 7. WebKit protection boundary — SPEC-08 / REQ-22

The app controls profile-to-store UUID assignment, nonpersistent private configuration, view ownership/generations, supported data inspection/deletion and whether it makes a backup claim. WebKit owns website-data paths, cookies, LocalStorage, IndexedDB, service-worker state, CacheStorage, HTTP/disk caches, media/authentication data and process lifetime.

Public APIs expose identifiers/type records/cookie operations and supported deletion callbacks; they are not a general encrypted-container key setter or complete portable session exporter. Do not attach the profile SQLite key to an assumption about WebKit's files. Cookie/storage exports do not reconstruct all authentication/service-worker/HTTP-auth/media-key state. Use only supported category-specific mechanisms, verify scopes/reopen and report limitations. [WebKit profile API](https://webkit.org/blog/14423/building-profiles-with-new-webkit-api/).

Release WKWebViews before identifier removal, await completion and handle in-use/filesystem failure; removing from a window alone is not enough. Enumeration, not init(forIdentifier:), is the noncreating existence check. [Apple removal API](https://developer.apple.com/documentation/webkit/wkwebsitedatastore/remove%28foridentifier%3Acompletionhandler%3A%29).

Current native observations are limited to marker sharing/isolation, CacheStorage and worker registration/readiness; no full cache/worker execution or at-rest protection guarantee. Original EXP-01 FAIL and the in-removal crash remain preserved. No original-store cleanup is attempted here. WebKit data is excluded from portable backup until reliable per-class export/restore/migration is demonstrated; unsupported required behavior remains an approval blocker. WKWebView conditional acceptance and ADR0001 Proposed are unchanged.

## 9. Existing package and authority boundaries

BrowserDomain/BrowserPorts expose opaque, native-validated scoped lease identities and typed outcomes, never DEK/KEK bytes, CryptoKit objects, SecItem dictionaries or SQLCipher connections. BrowserCore owns policy/epochs and cannot turn an ID into authority by itself. Native Host key broker owns Keychain/CryptoKit and export authentication; BrowserPersistence consumes a bounded current key lease internally for its qualified provider/worker. WebKit adapter never receives the profile SQLite key. No fifth package, production crypto implementation or frontend secret channel is introduced.
