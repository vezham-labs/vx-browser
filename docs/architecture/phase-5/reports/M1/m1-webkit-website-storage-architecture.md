# Vezham WebKit-managed website storage architecture

Version1.0 — Proposed, 2026-11-09 (Asia/Kolkata). **Documentation/design only; no production implementation or runtime authorization.** Baseline `timeline` at `a99da90d4d2ec7fbcb6308689709558641cf2b73`, parent `fb3a71668f92deef88cc61ef454eda202fbc2587`; initially clean.

[Qualification plan](m1-webkit-website-storage-qualification-plan.md) · [Traceability and SQLCipher applicability](m1-webkit-website-storage-traceability.md) · [Evidence](../../evidence/20261108T202200Z-webkit-website-storage-design/README.md).

This is a supporting SPEC-08 design under the current [Developer Specification](m1-developer-specification.md), [owner register](m1-owner-decision-register.md) and [boundary contracts](core-boundary-contracts.md). It integrates engine storage with proposed M1 contracts and planned M2/M5/M6/M8 work; it is not an M2 implementation/qualification report. No reports/M2 folder or completed M2 qualification exists in this baseline. Existing contracts, owner policies, ADRs and historical evidence are unchanged.

## 2. Ownership and trust boundaries

| Component | Owns | Does not own / expose |
|---|---|---|
| BrowserDomain / BrowserCore | ProfileId, persistent/private tagged scope, opaque storage binding, lifecycle policy, authorization, generations, pending effects and truthful state | WK objects, engine directories, website SQL/schema, raw cookies or native secrets |
| BrowserPorts | Typed resolve/provision/construct/quiesce/clear/remove/reconcile intents and bounded results | Generic execute-SQL, arbitrary path, arbitrary JS or a caller-selected WK object |
| BrowserPersistence | Vezham catalog mapping/intent/tombstone metadata, browser history/bookmarks/preferences/session descriptors/grants/download metadata and approved archive records | Cookies/localStorage/IndexedDB/service-worker/cache implementation or WebKit file manipulation |
| Swift/AppKit host + native EngineStorageCoordinator | Main-actor public WebKit calls, actual object/reference registry, immutable view binding, callback context, resource/lifecycle coordination | Product policy inferred from a page/renderer or a frontend UUID |
| WK engine adapter | Opaque engine descriptor → WK store resolution; view construction, navigation and public storage capability translation | Authoritative browser history, encryption policy or global cross-profile repositories |
| WebKit / OS | Website storage formats/paths, network/content processes, cache/quota/eviction/partitioning and engine-managed credential behavior | Vezham catalog consistency, owner decisions or app per-profile encryption guarantees |
| Future React/TypeScript/HeroUI v3 chrome | Sanitized status and explicit scoped user intents | Raw store UUID/object, native authority, cookie contents or engine files |
| Website content | Its engine-mediated web storage subject to web security policy | Browser-native dispatch, profile choice or persistence authority |

Same-process Host/Core modules are not security sandboxes. A store UUID is an identifier, not a capability. Engine-managed sub-processes do not imply a separate process/OS account per profile. No cloud/Tamizhi service participates in resolving, using or deleting local storage. A future chrome WKWebView, if selected, needs its own separate explicit store and trust context; it never shares a website/profile store merely for convenience.

## 3. Typed binding and catalog contract

Propose a browser-owned `WebsiteStorageBinding` value: BindingId, ProfileId, adapter kind/version, opaque engine descriptor, mapping revision, generation, lifecycle state, materialization observation, pending operation and privacy/deletion epoch. For the WK adapter, the descriptor contains one stable nonzero UUID distinct from ProfileId. WK object types and filesystem paths remain native-only. BrowserPersistence stores the opaque versioned descriptor in the protected catalog; Core carries the binding identity/state, not a WK class. This refines existing Domain/Ports/Core/Persistence ownership without adding a fifth core target or provider implementation.

**WSR-01:** one persistent profile maps to one unique active WK identifier in this app/container namespace; independent profiles cannot share it. Enforce uniqueness, immutable live-view scope and revision/generation checks. Persist the mapping before the first native construction effect; reuse it across app relaunch. Tombstoned/unknown identifiers are never silently recycled. A bundle/container identity change is a migration condition, not permission to reuse another app's namespace or derive a profile from a directory name.

**WSR-02:** resolve through trusted native AuthorityContext and a valid catalog lease. Missing catalog key/access, malformed/zero identifier, duplicate or foreign mapping, unknown version, namespace mismatch or retired generation blocks before factory/view/load. Never fall back to `.default()`, another profile, a new random UUID or a regenerated catalog/key. SQLCipher unavailability can block production catalog resolution; an isolated engine probe may use an explicitly synthetic fake catalog without claiming production persistence qualification.

For an established binding, use public identifier enumeration as a noncreating observation. An unexpected absence or inconsistent result becomes Missing/Unknown, with no named-factory “check.” Preserve mapping/data and expose a coarse blocked recovery state. Enumeration alone cannot authenticate ownership or guarantee a store's contents are intact. Unknown orphan IDs are not adopted, merged or deleted; do not sweep all identifiers or the default store.

Fresh provisioning differs from reopening: commit a Provisioning intent with its new UUID, then permit only that operation to create/resolve it. Object identity/persistence checks allow bounded fresh construction, but do not prove on-disk materialization. Track Virgin/AccessStarted/ObservedExisting separately; record AccessStarted before views/loads can touch the store. A brand-new unmaterialized binding is not treated as a lost existing store. After any uncertain access/crash, absence is not proof it was unused; quarantine instead of silently recreating. Required materialization/relaunch behavior needs qualification, not an assumption that factory return immediately creates an enumerable directory.

## 4. Construction and immutable store assignment

**WSR-03:** native coordinator resolves the intended persistent object or one session-owned nonpersistent object, validates context/state and assigns it to a fresh configuration **before any getter, view constructor, navigation or user-script activity**. After assignment verify persistent/isPersistent and expected identifier, or nonpersistent status plus native session-instance identity. Nil identifier alone cannot distinguish default from private. A nonpersistent object must originate in the native private-session registry; never archive WK objects with NSSecureCoding or decode a configuration as a binding.

Only the reviewed construction path may instantiate website views. Reject default initializers, coder/storyboard paths, omitted assignment and foreign popup configurations. Do not obtain `.default()` merely to compare object equality or warm up WebKit: that can itself instantiate a default store. A static construction audit plus future instrumentation is required; a log claiming “assigned” is not proof of the copied configuration. Native exception-prone nil/zero values are rejected before the API rather than deliberately passed through production.

**WSR-04:** store binding is immutable for a view lifetime. Switching profile retires/fences old view/request/subscription generations and creates a new view under the destination binding. Moving a tab across profiles cannot transplant its live renderer, cookie jar, pending grants or form/POST state. Any retained navigation descriptor follows existing Core policy; it does not become automatic action replay. Popups/new windows need native validation of supplied configuration/scope before creation; a web page cannot choose an arbitrary profile. For a new native configuration, never inspect an unset store through its getter. A supplied popup configuration has no public noncreating “store was explicitly assigned” probe; unverified configurations/popups remain refused until its supported inheritance/validation path is qualified. Do not use private getters or pretend a replacement configuration necessarily satisfies the popup API. This rule also covers future chrome/content separation.

## 5. Private-session lifetime and storage classes

**WSR-05:** each independently owned PrivateSessionId has one newly created nonpersistent store. Views intentionally in that same native group may share the object; independent groups and persistent profiles must not. Private policy/grant/permission/download-history/session metadata stays in browser memory. Never persist private store objects, session UUIDs, browsing markers or cleanup/recovery receipts to a catalog. Aggregate synthetic test results are not product private-history records. UI rules for joining private windows must preserve the existing intended-group rule; this document does not select an automatic grouping UX.

**WSR-06:** last-owner teardown fences new requests/results, cancels/reconciles owned operations, retires callbacks/delegates/message handlers/configurations/views/tasks and releases coordinator/store references. A reference count in Core, stopLoading, removeFromSuperview or a closed NSWindow alone does not prove engine release. Network workers, downloads, async closures and externally retained configurations must be inventoried. No private restoration after quit/restart/crash; fresh runtime IDs and a new private store. Explicitly saved user files can remain; profile/metadata deletion cannot silently delete them. OS memory/swap/crash/snapshot behavior is outside a secure-erasure claim.

| Class | Expected scope for qualification / limitation |
|---|---|
| Cookies, including HTTP-only | Same intended persistent/private group and applicable host/path/SameSite policy; observe HTTP-only via controlled server/cookie API, never JS alone. No global HTTPCookieStorage fallback |
| localStorage, IndexedDB | Profile/store plus web-origin/partitioning rules; exact same-origin positive controls needed. Unsupported/blocked web API is not proof of isolation |
| sessionStorage | Browsing-context scoped; do not expect all same-profile views to share it or restore it after app death. Popup opener semantics need a separate explicit oracle |
| CacheStorage / HTTP cache | Distinct classes with separate positive controls and server request/body evidence; marker absence alone is insufficient |
| Service workers | Registration/readiness is weaker than execution, controlled-client fetch and offline behavior. Private-mode availability must be measured per supported runtime |
| Other public types | Inventory allWebsiteDataTypes per runtime and capabilities. Public deletion enumeration does not imply export, portable restoration, at-rest encryption or universal origin granularity |

WebKit may evict data, restrict third-party storage or partition by top-level site. These are engine behavior, not permission to mix browser profile ownership. Profile mapping does not replace web-origin security or authorize account/MFA/SSO claims.

## 6. Profile locking, shutdown and crash recovery

**WSR-07:** on manual/OS/inactivity lock, immediately fence Core/native admission and result delivery for that profile; retire permission/file grants and view generations; execute the qualified engine view/operation barrier; retire Vezham key/DB access independently. Other profiles remain independently governed. Locked is reported only after the mandatory access barrier is demonstrated; unsupported suspension/background-worker behavior yields AccessBlocked/CleanupRequired, not UI-only lock success. No public API shown here encrypts or cryptographically revokes WebKit files with the profile key. Do not relax OD-R18 or claim that SQLCipher key retirement solves engine locking. OS trigger/native authentication/Keychain tests remain separate EXP-04/05 scope.

**WSR-08:** graceful shutdown quiesces views and effects before ending native ownership. WebKit exposes no universal all-data durable-flush/crash-repair contract through these APIs. Preserve Vezham metadata/operation outcomes with existing repository receipts and report pending engine work honestly. On restart, OP-04 controls normal/restart restoration and crash prompting; private sessions, pending requests/grants, forms/POST and renderer authority are never restored.

Content-process termination retires the affected registrations; a replacement view gets fresh generation while a persistent profile retains its mapping. Content and network processes may serve more than one view/profile: do not assume a per-profile PID boundary or kill a global/shared engine process. After host/network crash, reconcile established/Provisioning/Deleting/Restoring mappings via public noncreating observations and retained intents. Unknown outcomes remain blocked. Cookies/database validity and exact last-write durability require real relaunch evidence; the coordinator cannot repair WebKit SQLite files directly.

## 7. Website-data deletion versus removing a store

**WSR-09 — Clear selected website data:** authorize scope, data types and date/record selection; quiesce/restrict writers so deleted data is not immediately recreated; retain the native store/operation context. Use only public data-removal APIs and native-fetched records. Their completion callbacks have no error result; callback delivery is not a per-class verification or secure-erasure certificate. Verify selected classes with positive controls and fresh owned observations; retain residual/unknown state on timeout/crash. `modifiedSince` is engine modification-time semantics, not browsing-history visit time. WKWebsiteDataRecord is domain/public-suffix grouped, so displayName is not an exact origin/capability token. Never promise narrower per-origin deletion than the API/class supports.

Browser history, cookies, website data, cache, download history and permissions retain independent controls under OD-R12. Deleting engine cookies cannot silently clear browser history/grants; deleting download metadata cannot delete payloads. The UI-to-data-type bucket mapping must be explicit/versioned and reviewed; broad allWebsiteDataTypes cannot silently include unchecked cookie/cache/permission categories, and an unclassified newly introduced type is not automatically cleared. All-data-types clearing is not whole-store removal and does not authorize changing the catalog binding. If an empty store becomes temporarily unenumerable, preserve the clear intent and classify the observation; do not recreate it as a diagnostic or silently replace the mapping.

**WSR-10 — Remove the persistent store:** persist a deletion intent/tombstone for the exact binding before effect. Refuse new owners and do not force-close active work by convenience; settle views/transfers/operations and prove release scopes, including local/configuration references. Call the public remove-by-identifier method on the main actor in a valid app lifecycle, with before-call/store/op checkpoint and after-callback error checkpoint. Keep the app alive until a bounded terminal outcome. No `.default()` warmup, private API, manual engine-directory deletion or sandbox relaxation is a remedy.

Track Requested → Quiescing → RemovalPending → RemovedObserved / FailedOrPartial / Unknown, followed by catalog reconciliation. Success requires the error-free callback plus scoped noncreating absence observation and generation checks; label this logical removal only. A callback error may follow partial engine/credential/file effects (S: UP-04); directory presence does not prove intactness. Missing callback plus directory absence does not prove completion. Keep tombstone/mapping and block reopening on ambiguity. Catalog commit failure after engine success also stays pending reconciliation; never roll back to Active and call the constructor, which could recreate empty storage. No unchanged retry loop or deletion of unrelated/default/orphan stores.

The qualified lifecycle must distinguish completed removal, observed absence, retained artifacts, incomplete verification and physical erasure; only the first four are observable within declared scope. Do not promise secure erasure, deletion of user/OS backups, revoke old offline copies or deleting external downloads. Existing originals from failed experiments remain untouched by this design.

## 8. Backup, restore and migration

**WSR-11:** default current coverage is Vezham-owned protected metadata/archives under existing specifications; WebKit classes remain explicitly excluded until qualified. macOS26's public fetchData/restoreData methods are a candidate path, so do not declare that no API exists. Conversely, do not feed allWebsiteDataTypes into export and call the result a full browser backup. At the inspected upstream commit the accepted export class is localStorage; this is not a guarantee for the installed/minimum runtime. Cookie APIs offer separate limited operations, not a selected portable authenticated-session backup. IndexedDB, worker/CacheStorage/HTTP caches, credentials and other classes have no qualified coverage here.

The installed SDK also declares macOS26 per-view WKWebViewDataTypeSessionStorage export/restore. That is a separate browsing-context API, not persistent store export or a selected automatic session-restoration policy. Its page-state sensitivity/replay implications and lifecycle/backup coverage remain separately unqualified; do not assume it requires macOS27 or include it by default. Treat a returned blob as sensitive website content, not safe diagnostic metadata. Any future retained/exported blob needs the already specified encrypted archive/envelope/access/recovery controls and an explicit class manifest; this does not encrypt WebKit's live files using Vezham keys. No blob or encrypted fixture is produced here. Keep opaque bytes opaque: upstream internal serialization is not a stable application format contract. Manifest producer OS/WebKit/API versions, requested/actually qualified types, source profile/binding generation, privacy/deletion lineage, snapshot point, digest/size and limitations; never export raw engine paths or Keychain handles.

**WSR-12:** restore only to an explicitly staged new named binding, never a live destination store or private session. Validate Vezham archive/manifest versions and declared capability coverage before WebKit calls. Runtime must prove what provider parsing/errors/partial effects mean; a restore error is not an atomic rollback guarantee. Preserve archive/source/old binding, verify exact per-origin records and unrelated data, then publish catalog/binding changes through a recoverable saga. No implicit identity remap, overwrite, merge or path reuse on conflict. Interrupted restoration stays unpublished/Unknown; native public removal of a failed stage is its own qualified cleanup operation.

**WSR-13:** there is no shared transaction spanning catalog, profile SQLite, WebKit processes and external files. Coordinate quiescence/generations and versioned capture/promotion intents; do not claim a coherent snapshot from unsynchronized successful callbacks. Cross-Mac migration needs an independent destination, offline restore, supported producer/consumer matrix and explicit excluded-class disclosure. Copying opaque UUID directories/live engine databases or poking private filesystem layouts is not selected. Re-sign/container changes and missing mappings require reconciliation, not default-store import. Deleted-data reconciliation follows OD-R17/EXP-08: known records applied; unknown lineage requires explicit confirmation and disclosure, never a guarantee old offline backups know later deletions. External downloads stay excluded by default with OD-R20 selection/no-overwrite rules.

## 9. Logging, permissions and at-rest limits

**WSR-14:** log only coarse operation/status/data-class/version and opaque correlation/generation. No cookie values, tokens, URLs/query/fragment, localStorage keys/values, IndexedDB data, page console output, raw NSError paths/messages or private session identity. Synthetic fixtures may retain registered public markers only in isolated evidence with declared coverage. App log redaction cannot control every WebKit/OS log or crash dump; upstream removal logs identifiers and internal credential handling exists. These are limitations to review, not claims that OS logs are sanitized or that store removal cannot touch engine-managed credentials.

**WSR-15:** profile/store association does not grant website/native permissions. Apply Core origin/capability/profile/revocation policy and independent TCC/OS enforcement; unknown/ambiguous requests deny. No global credential/cookie service bypass. Restore does not restore native file tokens, device grants, active authentication context or private decisions. Real accounts/media/Keychain activity needs its existing separate authority; synthetic policy checks do not qualify native affirmative support.

**WSR-16:** WebKit-managed website files are a separate protection domain. The named UUID API provides no Vezham DEK injection, encrypted-volume-per-profile primitive, cryptographic lock or secure-erase API. OS/App Sandbox/FileVault protections may contribute under a recorded deployment configuration, but no actual protection level is established by this task. Do not wrap, rekey, open or replace WebKit SQLite/WAL/SHM with SQLCipher. Reuse of SQLite internally does not make its schema/files browser-owned. If required at-rest/lock/backup behavior cannot be demonstrated with public APIs, keep the feature/gate blocked and bring the actual conflict to owner/security review.

## 10. Unresolved decisions, assumptions and next milestone

Current OD-R06/07/10/11/14/17/18/20 and OP-01–04 already set the direction; they are not reopened or implementation authorization. Remaining product/security questions are: the launch-critical website-data classes and acceptable disclosed backup exclusions; the required protection level of engine-managed data if OS/public-API protections cannot meet it; any desired deletion UX finer than public domain/type granularity; and private-window grouping UX beyond the already mandated intended-session boundary. These become decisions only where existing policy does not determine the choice; none is decided here. Failure to meet the approved lock barrier cannot be silently accepted as a weaker lock.

Technical assumptions remain unqualified: accurate namespace/mapping observation, main-actor/framework lifecycle correctness, complete release of native references, no stale result acceptance, per-class private/persistent behavior, background activity stoppage, removal and export/import error semantics, cross-version format support and supported macOS26 behavior. The existing source snapshots are not installed-engine provenance.

Recommended next milestone: separately authorize **WS-F0**, a fake engine-storage port/catalog/lifecycle model and construction-path review, with no WebKit/SQLCipher/Keychain runtime. Its finite cases should prove no default/missing-binding fallback, immutable scopes, last-owner policy, late-result fencing and truthful deletion/restore saga outcomes. Before any native probe, resolve the historical removal-state/cleanup-crash diagnostic prerequisite and approve an exact new isolated harness/fixture manifest and platform scope. Do not restart the prototype or launch experiments through this document.

All ADR statuses remain unchanged (0001 Proposed/conditional WKWebView,0002 Accepted,0003–0005 Proposed). macOS26+, internal-only, Swift/AppKit host, Swift6 engine-independent Core and future React/TypeScript/HeroUI v3 are preserved. CEF remains evaluation-only; Aura and production Tamizhi are excluded; identity/cloud stays optional. No public distribution or release authority.

**No production code, dependencies, ADRs or owner decisions were changed. No WebKit/Keychain runtime, SQLCipher/provider operation, database open/create, encrypted fixture, build or runtime test was executed.**
