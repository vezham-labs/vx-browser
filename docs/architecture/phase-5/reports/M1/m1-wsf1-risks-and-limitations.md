# WS-F1 risks and limitations

2026-11-09. [Closeout](m1-wsf1-closeout.md) and [results](m1-wsf1-qualification-results.md) determine actual status; code and APIs alone prove no native guarantee.

- The available host is macOS27.2/26B123, arm64. Actual26.0/latest26.x qualification remains blocked. Deployment26.0, SDK27.2 and upstream source are different evidence classes; Intel and cross-Mac behavior are unqualified.
- Cold class-only identifier enumeration crashed in framework callback dispatch. The configuration-initialization change is based on pinned upstream API-object construction, not shipping-source identity or proof of a general engine defect. Preserve the original crash and every retry result. Historical original cleanup states remain unknown even if current enumeration observes presence/absence.
- Named-store resolution can create missing storage. Pre-observation narrows the hazard but does not create an atomic catalog/WebKit transaction. Unknown mappings, tombstones and interrupted operations must not auto-recreate or publish.
- Weak-reference disappearance and empty owned registries do not prove every engine process/task/network worker has stopped. Full lock barriers, external native references, background workers and key revocation remain mandatory unqualified behavior. A sticky native content-process fence is not cryptographic revocation.
- The final observed-release budget is15seconds; earlier2-second private teardown failures remain recorded. The final finite27.2 run met the revised budget without weakening the postcondition. This is not a2-second cleanup/performance pass. Hostile native grant/publication/callback races and complete production navigation identity/sequence contracts remain unqualified.
- The normal host has no approved protected durable catalog path. Qualification metadata is synthetic and mirrored through parent evidence; this is not a replacement JSON production database, encryption or crash-safe disk backend. Persistent product state still depends on the separately qualified BrowserPersistence/key workstream.
- Selected clear callback plus empty public records is not physical erasure or complete page-state proof. Record grouping is domain-based, not necessarily exact origin; time-based and all-category controls still need their oracles. Writer races and partial effects can survive an operation error.
- Removal may fail in-use or after partial effects. Missing callback/absence alone cannot finalize a tombstone. Uncertain identifiers/staging resources remain fenced and must not be reused or manually removed by engine-path manipulation.
- Nonpersistent stores and memory-only private metadata do not promise protection from OS swap, memory inspection, crash reports or diagnostics. Explicitly saved external files are independent; no metadata/profile deletion may silently delete them.
- WebKit website data is not encrypted by Vezham profile keys. SQLCipher covers Vezham-owned persistence only; D2A-01 remains unresolved. No WebKit-owned SQLite/WAL/SHM is opened or wrapped by Vezham. WebKit may internally use databases/credential services; absence of direct app APIs is not OS-wide nonactivity proof.
- No website-data backup/export/import is implemented or qualified here. Public macOS26 APIs do not imply complete, authenticated, stable or cross-version portable archives. Full backup and independent recovery/deletion-lineage/external-download policies remain unchanged.
- Media, upload, popup, authentication and unsupported response routes are conservatively refused; this does not implement the owner's eventual Ask/grant/revoke product workflows. Public-pages-only restrictions still block signed-in/MFA compatibility claims.
- No browser chrome, dynamic plugin, CEF runtime, Aura, production Tamizhi, cloud/account requirement, release updater or public distribution is introduced. Ad-hoc signing is development-only. All mandatory security/release gates remain intact.

Remaining owner/security questions from the existing architecture remain explicit: launch-critical website-data/backup class coverage and acceptable exclusions, required engine-managed at-rest protection where public APIs cannot meet it, finer deletion UX where public grouping is insufficient, and private grouping UX beyond intended-session isolation. No weaker lock, encryption or cleanup policy is independently approved here.
