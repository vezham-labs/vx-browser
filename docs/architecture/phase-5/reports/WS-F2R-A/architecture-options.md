# Architecture options

A–D compare proposed designs, not current capability. A is the page-codec candidate with native custody; B is ordinary SQLite relying on OS protections; C is application-authenticated storage with native primitives; D assigns protections by data class and can use A or a qualified C backend for protected tiers. All four preserve public engine-owned storage. “Conditional” means a specification or qualification requirement. [Classification](data-classification.md), [owner requirements](owner-decision-traceability.md)

| Dimension | A · SQLCipher | B · native SQLite + OS | C · native encrypted records/files | D · tiered hybrid |
|---|---|---|---|---|
| Confidentiality at rest | Conditional page codec, key and sidecars; protects copied encrypted files | OS protection depends on environment; copied ordinary DB is plaintext | Conditional AEAD, nonce and leakage controls; outer metadata can remain visible | A/C for protected tiers; only low globals eligible for B |
| Integrity | Conditional page authentication plus separate product identity and freshness | Transaction integrity, no cryptographic tamper protection alone | AEAD per record plus authenticated set/completeness and freshness design | Authenticate sensitive catalog and profiles, validate low fields, coordinate manifests |
| Key management | Native wrapped scoped keys; raw binding in confined worker | OS secrets only; no per-profile DB key | Native wrapped keys, explicit purpose derivation and nonce/version policy | Shared native custody for protected tiers, independent recovery |
| Profile isolation | Per-profile DBs plus scoped ports; WebKit separate | Logical DB separation, weaker copied-byte protection | Scope-bound records or files; test substitution and open-state isolation | Separate named engine stores and owned resources under same scope fence |
| Profile locking | Close/fence handles and drop leases; D2A affects reopen | UI/operational fence possible; durable bytes remain readable under OS access | Quiesce/close and drop keys; stage all state transitions | Native events plus common lock barrier across backend and views |
| Key revocation | Invalidate generation, expire leases, close worker; copied recovery material independent | No DB key to revoke | Invalidate scoped keys and stale operations; rotate envelopes/records explicitly | Shared lifecycle plus per-tier revoke, no claim of erasing copies |
| Application crash behavior | SQLite transaction mechanism; authenticated WAL and fenced recovery require evidence | SQLite recovery, no cryptographic product admission alone | Stock SQLite transactions or app-defined generations and atomic publication | Typed pending receipts and per-resource reconciliation |
| Recovery | SQLCipher reopen + key recovery + fenced verifier | Simpler SQLite tooling, insufficient encrypted recovery for protected scope | Explicit authenticated recovery, freshness, format migration | Product archive independent of active backend; engine recovery separate |
| Backup and restore | Coherent logical snapshot or qualified ciphertext snapshot; no live raw file copy | Logical snapshot still needs protected export and deleted-data reconciliation | Sealed manifest/chunks; validate complete set before publish | Owned-only encrypted by default; optional validated engine extension separately |
| Deletion guarantees | Logical removal and key lifecycle; no secure-erasure claim | Logical SQLite deletion only, may leave artifacts | Logical deletion and record/key custody; no deletion of copies | Durable receipts for each owned/engine resource; external files separate |
| Migration complexity | Provider/suite/schema compatibility and authenticated old source | Standard schema migration, but protected data still cannot go to plaintext | Multiple formats/keys, indexes, anti-replay and copy-forward validation | One logical archive plus backend-specific verified staging |
| Performance | Query/index reuse, KDF and per-page CPU cost require measurement | Low provider overhead hypothesis, incomparable for protected data | AEAD per record, search/decode and write amplification risk | Lower overhead on truly low/volatile paths; protected and reconciliation costs remain |
| macOS compatibility | Exact build/signing/ABI/provider on 26.0 and latest 26.x | OS SQLite and security API behavior still version-specific | CryptoKit, Keychain and filesystem semantics require same baseline | Must qualify every selected tier and engine capability on both release targets |
| Maintenance burden | Vendor updates, build pin, runtime PQR and secure worker | Smallest database integration; leaves protection gaps for high classes | Largest security-owned design if custom indexes/journals/anti-rollback | More explicit classification/routing; avoid duplicate permanent backends |
| Operational complexity | Provision scoped key, native identity and broker/VFS; inspect state without unauthorized opens | Fewer provider artifacts, independent release/backup and OS controls remain | Recovery-kit, envelope, manifests and corruption tooling become product responsibilities | Keychain/custody shared, failure and lifecycle coordination still explicit |
| Testability | PQR plus lifecycle oracles; verify authentic binary and unchanged failure inputs | Useful baseline and low tier; not positive encryption evidence | Tamper, reorder, replay, truncation, crash, temp and leakage oracles | Reuse common lifecycle cases, add tier classification and end-to-end fences |
| Future engine independence | Achievable via logical ports/exports | Same product boundary | Same product boundary, avoid engine-tagged payloads | Makes binding and payload separation explicit |

## Feasibility filter

- **A** preserves the required SQL topology with the least novel persistent query engine. Existing-file access remains blocked at the current pin. Select only after the owner disposition and provider qualification. Its strongest fit is full persistent profiles and the sensitive catalog.
- **B** is appropriate for demonstrably low-sensitivity global state or disposable fixtures only under current policy. Extending it to full profiles would conflict with OD-R07 and related lock/backup/download protections. A low tier cannot mint profile identities, choose engine stores, grant authorization or recover protected data.
- **C** has two defensible design candidates. A stock SQLite ciphertext-record adapter retains the topology, stores authenticated encrypted payloads, minimizes visible structure and uses bounded in-memory search before considering any persistent keyed index. Review correlation/length/access patterns, replay, deletion, row-set completeness, transaction generations and independent freshness anchors. A sealed-file/limited RAM SQLite approach can fit small artifacts, with bounded chunks and durable manifest publication. Using it as primary profile storage would need an explicit OD-R04/05 policy revision. Do not introduce an ad hoc encrypted pager/VFS, disk image, plaintext transient file or whole-database copy workaround. [SQLite temp files](https://www.sqlite.org/tempfiles.html), [Apple CryptoKit](https://developer.apple.com/documentation/cryptokit)
- **D** is the recommended ownership and policy architecture. Encryption remains mandatory across each persistent profile and sensitive catalog state. Use the same logical ports and evaluate one protected backend at a time. A remains the leading candidate if D2A-01 and runtime gates clear. A bounded C design study is the alternative if the owner keeps the literal rule or the provider remains unsuitable. [Recommendation](recommended-architecture.md)
