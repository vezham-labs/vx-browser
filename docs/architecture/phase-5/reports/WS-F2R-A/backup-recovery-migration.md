# Backup, recovery and migration

**Proposal.** The portable format is Vezham-owned, backend-independent and encrypted. Keep per-profile archives and full-browser archives over an authorized catalog projection and selected persistent profiles. Exclude private data, live capability tokens, transient recovery work and website data by default. Browser policy cannot convert a WebKit directory copy into supported backup. A future optional engine member requires a public API coverage matrix, signed runtime validation and explicit product/security approval. An owned-only restore should provision a fresh named engine store for a restored/new profile through the approved lifecycle, with no expectation of website login or site data. [OD-R14, R17, R19–20](../M1/m1-developer-specification.md), [migration strategy](../M1/migration-and-recovery-strategy.md)

## Export and key custody

1. Validate authority, scope, live generation and manifest selection. Use a coherent logical snapshot under an authenticated reader with a stable catalog/profile generation barrier. A full-browser backup can stage independently consistent members under an explicit freeze/recheck and commit manifest, rather than claim cross-database atomicity. A raw copy of a live SQLite main file may omit WAL state. SQLite's backup API is an alternative snapshot mechanism if a particular destination and encryption policy are qualified. [SQLite WAL](https://www.sqlite.org/wal.html), [SQLite Backup API](https://www.sqlite.org/backup.html)
2. Define a versioned portable format independently of the catalog schema. The authenticated manifest binds archive format and suite, selected members and digests, scoped identities, logical schemas, key versions and deletion-knowledge state. Bound sizes, parsing, version compatibility, KDF parameters and chunk/nonce use. Admit only an explicit list of product records. Exclude actionable OS permissions, device credentials, raw keys, engine handles and uncommitted recovery entries.
3. Normal access uses a device-protected Keychain path and scoped leases. Recovery uses independent user-controlled material, locally generated with checked randomness, a printable kit and encrypted file. Authenticate purpose, scope, format and key version. Wrap archive keys with qualified recovery authority, verify saving/export and preserve an independent offline path across Macs. Record coverage before rotation/retirement and warn about permanent loss if both custody paths are lost. No Vezham account/cloud requirement. [Key and recovery specification](../M1/m1-keychain-and-independent-recovery-specification.md)
4. Default exclude actual downloaded files. Offer all or individual file selection and estimate size before copying. Record original authorized location, identity/digest and missing/moved/access-error state. Recheck at acquisition and validate content. External bytes need explicit authorization and encrypted archive membership. Deleting profile or download metadata does not delete them. [OD-R20](../M1/m1-developer-specification.md), [OP-02](../M1/m1-owner-decision-register.md)
5. Write encrypted staging at an authorized root, with stable directory identity, exclusive/no-follow creation, size limits and no overwrite. Verify complete file and manifest, publish via explicit commit protocol, fsync as specified, reconcile ambiguity after link/rename or cleanup failure and keep prior backups. A named file alone is not a success receipt. Quarantine or clean only demonstrably owned staging.

## Import, deletion and migration

- Authenticate envelope and manifest against independent recovery authority. Validate exact membership, identity, format, integrity and compatibility before admission. Distinguish wrong key, unsupported/newer version, corruption, unknown deleted-data state and permission refusal. Preserve source and archives for retry.
- Consult independent deletion records with known lineage and generation. Exclude deliberately deleted records where known. When knowledge is unavailable, name affected data and require explicit confirmation. Acknowledgment does not prove old offline backups lack later-deleted records. Define authenticated propagation, retention and pruning of deletion knowledge across devices and media. [OD-R17](../M1/m1-developer-specification.md)
- Stage a separately authorized new protected store. Run approved migrations with typed receipts, verify counts/content/identity and do not regrant native/site permissions from imported data. Establish valid scope and an independent engine admission decision. Use per-resource pending/committed states; expose only after all selected authoritative members commit. Crash, timeout, ENOSPC or unexpected final name yields fenced recovery with idempotent reconcile, never silent overwrite or destructive reset. External restore requires a user-authorized destination and explicit resolution of conflicts.
- Support offline restoration on a separate authorized Mac with no dependence on source Keychain or Vezham identity. Preserve old source, old key and prior backups until new-state verification and authorized retirement. For backend changes, migrate logical records from authenticated inputs. An old encrypted SQLCipher input still requires a safe open under applicable D2A-01 policy. No production input format was demonstrated by this source review; inventory authorized real formats before proposing any migration. Keep qualification fixtures out of production migration.
- For sessions, restore only eligible navigational descriptors, prompt after crash, keep recently closed reopen manual and preserve explicit user snapshots separately. Never replay POST/form submissions or restore private/deleted/locked state. Session restoration does not restore website credentials. [OP-03/04](../M1/m1-owner-decision-register.md)

## Evidence boundary

`OwnedBackupPolicy` bounds the synthetic input at 1,024 records, 64 KiB per record and 4 MiB total, filters known deletions, checks scope/generation and excludes active permission grants on restore. `EncryptedOwnedBackup` uses a synthetic in-memory recovery authority, CryptoKit AES-GCM/HKDF, provisional canonical CBOR and no-overwrite publication. Its authenticated header exposes some metadata and needs a disclosure decision in production. The publisher accepts bytes independently of archive verification; failure after link can leave an output needing reconciliation. The archived roundtrip, tamper/truncation, wrong key/scope, private, conflict and incomplete-stage controls do not qualify coherent production export, real Keychain custody, durable import or cross-Mac restoration. [Policy](../../../../../qualification/webkit-storage-f0/Sources/BrowserPersistence/OwnedBackupPolicy.swift), [archive](../../../../../apps/browser-macos/StorageRuntime/Sources/BrowserNativeStorage/EncryptedOwnedBackup.swift), [WS-F2 backup result](../../evidence/20261109T105707Z-webkit-storage-wsf2/f2-security-native-113238831637/backup-result.json)

Using stock SQLite simplifies provider-specific format/tooling for eligible tiers. It leaves transaction coherence, encryption of exports and staged protected records, manifest validation, independent key custody, deletion reconciliation and recovery intact. A ciphertext-record adapter transfers more integrity/search/version responsibility to Vezham. [Architecture options](architecture-options.md)
