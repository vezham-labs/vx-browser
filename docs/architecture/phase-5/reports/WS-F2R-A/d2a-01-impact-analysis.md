# D2A-01 impact and decision boundary

**Proposed / Not Decided.** The literal existing-file ordering rule remains in force. This reassessment authorizes neither option nor any runtime work. [Canonical OPEN-01 §4](../M1/m1-sqlcipher-open01-resolution.md), [owner decision record](../WS-F2R-owner-handoff/d2a-01-owner-decision.md)

## Why the pinned path cannot satisfy the literal rule

At the source pin, `src/main.c:3682,3712–3714,3729,3787,3809–3815` constructs the main B-tree and returns the connection. `src/btree.c:2575,2712–2716,2846` opens the pager and reads the initial database header. `src/pager.c:4074–4079` issues the read from offset 0 and `src/os.c:88–90` forwards it to VFS. The request is 100 bytes on the investigated path, with the default encrypted format containing salt plus encrypted bytes rather than a deliberately plaintext schema/header. Later `src/sqlcipher.c:3657–3681,3734–3755,3810–3822` binds the codec/key to a constructed handle. Derivation can occur later with the 16-byte salt. Exact I/O depends on the approved VFS and binary. [Source investigation](../WS-F2R-owner-handoff/d2a-01-initialization-feasibility.md), [source inspection manifest](../WS-F2R-owner-handoff/d2a-01-initialization-evidence/source-inspection.json)

`KeyReceived → KeyApplied → derive/authenticate as required → authenticated identity → DatabaseReady → write grant` are distinct, fenced milestones. Before key application the target read is already requested through the application/VFS boundary. Kernel cache, read-ahead and block granularity prevent deducing physical device I/O. VFS pointer hints, URI setup, extension and ATTACH flows do not supply a supported early handle. Opening memory first, reading/copying/hashing the target early, fabricating a header or deadlocking in `xRead` does not satisfy the policy. Exclusive creation or truthful EOF on a new file does not qualify existing-file reopen. [Rejected sequences and negative finding](../M1/m1-sqlcipher-open01-resolution.md)

## Options for the owner

- **Option 1 — retain literal zero pre-key target-byte requests.** Existing-file opens through this pin remain blocked. Continue only with an independently authorized, supported key-aware path or reconsider the provider. No fake data, hidden copy/read, provider patch, existing-file migration or weak interpretation.
- **Option 2 — approve the exact scoped exception in OPEN-01.** In the pinned qualification path, a validated scoped 32-byte key must already be in worker-owned memory. Permit exactly the truthful main-database request at offset 0, length 100, before the length-explicit key call. No extra reads, mappings, pre-key hash/copy, schema or row SQL, key in SQL/URI/logs, mutations, checkpoints, recovery writes, readiness or write grant. Apply the approved suite, then authenticate native scope, store, schema, suite and key version with the original files fenced. Unexpected range or mutation stops and preserves the run. Hashing if required starts after KeyApplied and before auth reads that might initiate recovery, with the fence active. The exception is an application/VFS request bound, not a bound on physical reads. Re-review on provider or VFS upgrades. Approval would still require separate implementation and runtime authorization. [Exact text and evidence oracle](../M1/m1-sqlcipher-open01-resolution.md)

## Security objective versus enforcement rule

The zero-read constraint is a mandatory baseline ordering defense and an implementation-level restriction. Its enforceability is distinct from whether pre-key ciphertext contains plaintext or whether a database can authorize state transitions. Reading a bounded encrypted header creates a changed exposure and parser/I/O ordering that the owner must explicitly assess. No claim follows about payload confidentiality, atomicity or authorization solely from that bound.

| Security objective | A · SQLCipher | B · stock SQLite + OS | C · authenticated application storage | D · tiered design |
|---|---|---|---|---|
| No plaintext schema/row exposure before authentication | Designed for encrypted pages under approved suite; raw header exception unresolved; test diagnostics and auth path | Protected schema/rows are plaintext at app layer; logical admission only | Key acquired before sealed input; authenticate before parse/publication; ciphertext-record structure visibility needs review | Apply A or C to protected tiers; keep low tier outside trust |
| No unauthenticated ready | Authenticated product identity and fence required after codec setup | Can reject invalid scope logically, lacks cryptographic protected identity alone | AEAD plus authenticated complete manifest/expected identity and generation | Protected catalog and store must both be ready before persistent admission |
| No unauthorized writes, migrations or recovery | Broker/VFS write fence, independently verified before recovery | Can gate app writes; no authenticated protected-store recovery alone | Scoped staging, explicit write grant and transactional publication | Common coordinator plus backend and engine receipts |
| No key in SQL, logs, URIs or diagnostics | Length-explicit native key binding and redaction, qualify binary and failure paths | OS key references for separate secrets only | Native leases and purpose-separated crypto, scrub all error paths | Shared host capability and no key transport to core/UI |
| Authenticated profile/store/schema/key identity | Authenticated binding above codec and expected host context | No equivalent for plaintext database alone | Associated data plus manifest, version and independent expected state | Authenticate each protected member and reject cross-tier substitutions |
| Wrong/corrupt/unavailable handling | No open on unavailable key; verify wrong/corrupt without mutation, preserve source | Can detect some corruption; no key-bound database identity | Typed no-access before key; tamper/corrupt deny and preserve | Per-member classification with one fail-closed admission barrier |
| Offline access protection | Conditional on actual build, sidecars, keys and exports | OS protection conditional; ordinary copied DB is plaintext | Conditional on key custody, leak/completeness controls, backups | Conditional for protected tiers, independent engine domain |

The SQLCipher-specific rule applies to **every retained existing encrypted SQLCipher database**: sensitive catalog, per-profile databases, and any authenticated migration/recovery source still using the format. Replacing a class's SQLCipher backend removes this pin's cold-open path for that class only. It does not waive key-before-content admission, mutation fences or provenance. For a C/D candidate, specify the new ordering and witness boundary explicitly before adoption. WebKit storage, volatile private state, already sealed native artifacts and low approved preferences do not need a SQLCipher open. Neither option is selected here.
