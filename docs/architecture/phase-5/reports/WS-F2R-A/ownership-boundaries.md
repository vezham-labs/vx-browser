# Storage ownership and trust boundaries

| Authority | Owns | Boundary |
|---|---|---|
| WebKit | Cookies, LocalStorage, IndexedDB, HTTP cache, service workers, origin storage, records, persistent/nonpersistent stores and internal formats | Native adapter uses public store, clear and remove APIs. Vezham chooses scope and coordinates lifecycle. WebKit implements the website-data effects. |
| Vezham Core and Persistence | Browser policy, authoritative profile and scope, tabs and sessions, history, bookmarks, product settings, receipts, grants and backup manifests | Product repositories receive typed scope and operate behind a fence. Engine payloads and website credentials do not enter these repositories. |
| Native Host and macOS | App lifecycle, views, user authorization, Keychain, OS permissions, entitlements, sandbox, file capabilities and random generation | OS authorization remains independently necessary. Core grants and host presentation cannot supersede it. Key handles remain native and scoped. |
| User/external filesystem | Files explicitly saved or selected for export/backup | Browser metadata contains authorized references. Metadata deletion cannot authorize deleting the file. Restore requires explicit selection and conflict handling. |

Source review of `NativeWebKitStorage`, `NativeStorageSession`, the scope model and storage ports found an adapter around public lifecycle calls and persisted-binding design, with no runtime mirror of cookie jars, WebKit SQLite files, website records or origin payloads in Vezham storage. The native mediator intercepts **permission decisions**, not website persistence. Qualification page scripts seed synthetic data through page APIs. Static review does not inspect WebKit internals or qualify effects beyond archived observations. ## Public API availability

Inspected installed macOS 27.2 SDK, `System/Library/Frameworks/WebKit.framework/Headers/WKWebsiteDataStore.h`. The table distinguishes SDK declaration from product runtime. The first four API families inherit the class macOS 10.11 availability. The target baseline stays macOS 26.0.

| API | Header and macOS availability | Boundary and current use |
|---|---|---|
| `WKWebsiteDataStore.default()` | 43, 47 · 10.11 | Shared default store. User-content views must never select it. Adapter constructs a cold configuration, assigns the scoped store, then creates the view. |
| `nonPersistent()` | 53 · 10.11 | New nonpersistent store. Retain and share within one intended private session only. No durable mapping or restoration. No claim about all OS artifacts. |
| `init(forIdentifier:)` | 109 · 14.0 | Returns/creates the UUID-named store. Reserve a stable, nonzero ID separately from ProfileID. Missing existing storage triggers recovery, never implicit fresh creation. |
| `fetchDataRecords(ofTypes:completionHandler:)` / Swift async `dataRecords(ofTypes:)` | 68 · 10.11 | Metadata view of supported records. The async call is used for bounded post-clear checks. Record grouping is not an exact-origin proof or full export. |
| `removeData(ofTypes:for:completionHandler:)` | 75 · 10.11 | Record-based removal. Product record-specific workflow unqualified. Grouping and supported kinds need explicit tests. |
| `removeData(ofTypes:modifiedSince:completionHandler:)` | 82 · 10.11 | Adapter clears selected kinds from `distantPast`. Product cutoff/retention semantics for website data are separate from history retention. |
| `identifier`, named store remove and enumerate | 90, 117, 123 · 14.0 | Identifier is nil for default and private. Enumerate without creating. Retire views and release store references before requesting full removal. Verify absence by enumeration, never by looking up the deleted ID. |
| Opaque `fetchData(of:)` / `restoreData` | 96, 102 · 26.0 | Header restricts coverage to specified data types and documents error behavior. The runtime does not use these methods. They do not establish portable, complete or reliably restorable website data. |

See [Apple WKWebsiteDataStore](https://developer.apple.com/documentation/webkit/wkwebsitedatastore), [WebKit profile API introduction](https://webkit.org/blog/14445/webkit-features-in-safari-17-0/) and [qualification plan](../M1/m1-webkit-website-storage-qualification-plan.md).

## Lifecycle rules

1. Authorize scope and reconcile the durable mapping and generation before resolving a store. Create only for an explicitly reserved fresh mapping. Reject mismatch, missing existing stores and default-store fallback. Treat enumeration/lookup races as qualification cases.
2. For a switch, rebind new views before construction under the new scope. Cancel stale results and avoid reusing a view across profiles. Keep other profiles independently operable.
3. For lock, shutdown or crash, close admission first and fence late work. Retire/suspend scoped views, revoke product key leases and leave private sessions out of relaunch. Resume persistent scope only after authenticated resource reconciliation.
4. Clearing selected data types preserves the named store and mapping. Full removal fences the profile, retires resources, requests named-store deletion and checks absence. Error, timeout or uncertain completion yields a retryable or quarantined state with durable receipts, not a successful deletion or a replacement store.
5. Request external data effects only through documented APIs. Redact origins, URL contents, titles, key bytes and paths from diagnostics. Record opaque scope/generation, operation, phase and typed outcome. Website permissions remain scope/origin/capability-bound and OS authorization remains separate. ## Native protection inventory

- **Keychain and random generation.** Data Protection Keychain and user-presence ACLs protect scoped secrets and can require interactive authentication. They do not encrypt arbitrary database files or revoke bytes already in application memory. Current source uses checked `SecRandomCopyBytes`, `WhenUnlockedThisDeviceOnly`, non-synchronizing GenericPassword items and scoped leases. The observed entitlement failure prevents qualifying that path. [Apple TN3137](https://developer.apple.com/documentation/Technotes/tn3137-on-mac-keychains), [SecRandomCopyBytes](https://developer.apple.com/documentation/security/secrandomcopybytes(_:_:_:)), [native code](../../../../../apps/browser-macos/StorageRuntime/Sources/BrowserNativeStorage/NativeKeychain.swift)
- **FileVault and Data Protection.** FileVault protects the volume at rest under its platform conditions. macOS Data Protection classes have hardware, login and open-handle semantics. FileVault, default containers and class attributes do not create an independent profile key, govern exports or implement application-profile locking. The inspected Foundation `NSFileManager.h:1302–1317` exposes some classes; `CompleteWhenUserInactive` is unavailable on macOS. Core Data `NSPersistentStoreCoordinator.h:166` marks `NSPersistentStoreFileProtectionKey` unavailable on macOS. Any specific class, ACL and hardware claim needs a signed runtime check. [Apple FileVault](https://support.apple.com/en-nz/guide/security/sec4c6dc1b6e/web), [Apple Data Protection classes](https://support.apple.com/en-ca/guide/security/secb010e978a/web)
- **Sandbox, signing and OS access control.** App Sandbox, protected app containers, file permissions and user-mediated file capabilities restrict access under OS rules. Signing, entitlements, Hardened Runtime and consent are distinct checks. Qualification must prove the actual team/app identity and access-group continuity, least privilege, and authorized file roots. A compromised trusted process or authorized override remains a separate threat. [Apple App Sandbox](https://developer.apple.com/documentation/security/protecting-user-data-with-app-sandbox), [Apple protected containers](https://developer.apple.com/documentation/xcode/protecting-local-app-data-using-containers), [Apple sandbox file access](https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox)
- **Database, filesystem and CryptoKit.** Ordinary SQLite provides transactions, journals and snapshot facilities without application-level ciphertext or authenticated identity. CryptoKit can supply authenticated encryption and key derivation for owned artifacts. It supplies neither transaction/durability semantics nor deletion reconciliation. Atomic name publication, directory identity, no-overwrite, crash recovery and temp paths need separate contracts and tests. [SQLite WAL](https://www.sqlite.org/wal.html), [temporary files](https://www.sqlite.org/tempfiles.html), [Apple CryptoKit](https://developer.apple.com/documentation/cryptokit)
