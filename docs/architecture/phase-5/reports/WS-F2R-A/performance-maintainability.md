# Performance and maintainability

All option comparisons are engineering hypotheses. Archived native timings include discovery harness deadlines, not product persistence benchmarks or release performance. Keep prior Phase 3, WS-F1 and WS-F2 revisions separate. Fix device, OS, candidate build, signing, toolchain, data size, key/ACL mode, cold/warm conditions and concurrent scope count before comparisons. Record spread, errors and tail behavior as well as time. No performance threshold is inferred from this review. [WS-F1 results](../M1/m1-wsf1-qualification-results.md), [WS-F2 results](../M1/m1-wsf2-qualification-results.md), [Stage C](../../../../decisions/0001-browser-engine-strategy.md)

| Operation | Expected cost drivers by architecture | Future bounded measurement |
|---|---|---|
| Cold startup | A adds worker, Keychain, key setup and auth; B avoids page encryption but only qualifies as low tier; C adds manifest/record authentication and potentially index rebuild; D can defer unavailable nonactive scopes | Cold launches with representative catalog; report UI-ready vs authenticated profile-ready; separately time user presence and auth |
| Profile creation | A/B reuse SQLite creation; C needs sealed identity/manifest and nonce lifecycle; D includes independent engine reservation and key custody | Fresh creation, failure unwind, retries and other-scope responsiveness |
| Switching and lock/unlock | A close/reopen/auth costs; B lacks real key revoke; C clear memory indexes and reauthenticate; D adds scope barrier and view retirement | Two active profiles, in-flight IO, separate user-auth wait, measure blocked late work and handle drain |
| History writes and lookups | A preserves indexed SQL, page overhead; B plaintext control; C encrypted records may need bounded memory search and larger writes; D keep all profile history protected | Mixed writes, time/range delete and queries at multiple sizes; track I/O, WAL, memory and leakage |
| Bookmarks | A/B transactional tree updates; C AEAD per record and set integrity; D use same profile adapter | Import-size fixture, reorder/folder operations and malformed data; latency and atomicity |
| Session persistence | A page/transaction cost, C sealed snapshots/chunks and publication, D separates durable owned snapshots from volatile private state | Burst tab/window writes, idle checkpoint, explicit snapshot and process termination during flush |
| Keychain and recovery | A/C/D share signed custody and independent recovery. B only reduces DB-specific key work. | Valid/denied/unavailable Keychain operations; size-bounded restore and offline cross-Mac path. Separate KDF, user delay, decode and commit |
| Migration and recovery | A provider/suite, schema and sidecars; C authenticated format, completeness and freshness; D common archive plus selected adapter | Old/new/incompatible fixtures, interrupted runs, rollback evidence, consumed space and time |
| Testing and Swift integration | A requires native ABI, worker, provenance and PQR; B uses SQLite C API/OS variation; C adds Swift crypto and storage-format responsibility; D requires classification tests and one active protected backend | Count separately signed/OS/provider matrices, app failure paths, reproducibility of required witnesses |
| Long-term maintenance | A vendor updates and build chain; C custom format, leak reviews and recovery tools; D minimizes scope while preserving durable contracts | Track dependency patch cadence, compatibility commitments, burden of reviewer-owned invariants |

Choose release performance thresholds against approved workloads and report the exact stage/candidate. A simpler stack for low-risk data does not offset a failure on a protected tier. Do not trade cross-profile isolation, authentication, key lifetime or privacy for faster timing.
