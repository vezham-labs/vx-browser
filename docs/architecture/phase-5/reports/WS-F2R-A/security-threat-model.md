# Security and failure matrix

Protected assets include profile and catalog records, authority, encryption keys, backups and native file capabilities. Threats include malicious sites/renderers, compromised chrome messages, wrong scope, copied or tampered files, an untrusted local process, partial I/O and stale operations. Trusted code, the OS and authenticated host control are assumptions. A fully compromised OS, trusted app process or authorized key custodian is outside the claim. At-rest protection and authorization must both hold. No claim of secure erasure, complete private forensic cleanup, or engine portability. ## Common security oracles

- Missing/denied/mismatched authority stops before opening protected resources. Failed authentication never produces ready state, a write grant, implicit create, migration or unreviewed recovery.
- Use scoped synthetic fixtures; record signed identity, configuration, revisions, operation/epoch, monotonic phase, authorized read/write witness, byte hashes at permitted times, commit/recovery receipts, typed terminal result and independent controls. Preserve original files and sidecars. Distinguish missing evidence from success.
- Verify no plaintext across deliberately seeded sensitive storage, indexes, journals, temp, logs and exports within the documented observation scope. An offline copy test, entitlement verification and a physical-I/O claim are separate.
- Cross-profile leakage, unauthorized native access, unauthenticated readiness/mutation and private owned-state persistence are hard failures. Profile lock is a coordinated security boundary. WebKit sandbox and native OS authorization remain independent.
