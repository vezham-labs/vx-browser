# WS-F2R — D2A-01 SQLCipher Initialization Feasibility Investigation

## Objective

Investigate whether the current pinned SQLCipher integration can initialize and open an existing encrypted Vezham-owned database while preserving the strict zero-read-before-key policy.

This is an investigation and evidence-gathering task only.

Do not implement WS-F2R. Do not modify production code. Do not select or approve either D2A-01 option.

## 2. Owner policy — do not weaken

The strict policy remains the baseline:

**No database-content read before successful key application.**

Until D2A-01 is explicitly decided:
- No pre-key schema or row reads.
- No plaintext SQLite fallback.
- No pre-key database hashing or copying.
- No pre-key recovery/checkpoint writes.
- No key in SQL text, connection URI or logs.
- No database-ready state or write permission before authentication.
- No bypass of native scope, store, schema, suite or key-version identity checks.

Do not interpret this task as approval for the proposed 100-byte encrypted-header request exception.

## 3. Investigation questions

### A. SQLCipher initialization sequence

Inspect the pinned SQLCipher source and actual Vezham integration.

Establish the exact sequence required to:
1. Create a database connection.
2. Configure the VFS and connection.
3. Apply the encryption key using the supported API.
4. Configure required SQLCipher settings.
5. Perform the first database read.
6. Authenticate the encrypted database and validate its identity.

Identify any API that might trigger a database read implicitly.

Distinguish connection construction, configuration, key application and database authentication.

### B. Existing encrypted database opening

Determine whether an existing encrypted database can be opened without any application/VFS database-content read request before key application.

Investigate:
- SQLCipher APIs.
- SQLite connection initialization.
- VFS open, read and file-control behavior.
- Database-header access.
- Page-size and cipher configuration.
- Key application timing.
- First-read behavior.
- Error handling and authentication failures.

Do not assume that a successful API call means no read occurred.

### C. Instrumentation and evidence

Determine how to instrument the actual Vezham SQLCipher/VFS path to record:

- Connection construction.
- File open requests.
- File reads and offsets.
- Read lengths.
- Key-application invocation and completion.
- First database-content read.
- Schema authentication.
- Database-ready transition.
- Write authorization.

The evidence must distinguish:
- Application/VFS read requests.
- Underlying OS/device reads, which may include caching and read-ahead.

Do not claim physical zero-byte reads based solely on application/VFS instrumentation.

### D. Feasibility alternatives

Evaluate only supported, documented approaches.

If strict zero-read initialization is feasible, describe the exact sequence and evidence needed.

If it is not feasible, identify:
- The exact API or initialization operation that causes the conflict.
- Whether a supported SQLCipher API or VFS alternative exists.
- Whether another supported database initialization architecture is required.
- The security and operational trade-offs.

Compare these findings against both existing D2A-01 alternatives without selecting one.
