# Content-process recovery investigation

**Disposition: retain the existing fence.** The source trace is complete. The existing lifecycle can create a separate private session, but it does not yet demonstrate a safe, workspace-preserving replacement after a real content-process exit. This increment did not change code, launch a test candidate, signal a WebKit process or exercise any recovery path.

## Current behavior

1. The WebKit termination callback matches the view by object identity, then fences and poisons its scope. Admission checks reject surface lookup, navigation, construction and publication in that scope. `allowAcquisition` also refuses to lift a poison fence. Tabs and split panes using the same window session lose access together, even when only one callback arrives. A Mini owns a separate private session. This is source behavior. Actual callback delivery and process sharing remain unqualified for this candidate. [Adapter fence and callback](../../../../../apps/browser-macos/StorageRuntime/Sources/BrowserNativeStorage/NativeWebKitStorage.swift#L444) · [Admission guard](../../../../../apps/browser-macos/StorageRuntime/Sources/BrowserNativeStorage/NativeWebKitStorage.swift#L289) · [Window session factory](../../../../../apps/browser-macos/Sources/Host/MainWindowController.swift#L272)
2. Reload eventually calls the adapter's guarded navigation path. It cannot revive a poisoned scope. The main UI offers **End session** for unavailable content. Mini's generic reload/address instruction can mislead because those actions still target the fenced scope. Ending the session clears its tab order, pins, groups, Spaces and split state. [Native Reload](../../../../../apps/browser-macos/Sources/Host/MainWindowController.swift#L419) · [Main failure UI](../../../../../apps/browser-macos/Chrome/src/Browser.tsx#L452) · [Mini failure UI](../../../../../apps/browser-macos/Chrome/src/Browser.tsx#L335) · [Session discard](../../../../../apps/browser-macos/Sources/Host/MainWindowController.swift#L328)
3. The normal final-view close asks Core to quiesce and retire. The adapter stops loading, removes delegates and subviews, observes outstanding references, and checks private-store cleanup before reporting retirement. When Core close fails, the host instead fences and revokes through `discard()` and clears its UI state. That error path does not provide a successful retirement postcondition. A recovery action cannot treat an empty tab list or hidden split pane as evidence of release. [Core close](../../../../../qualification/webkit-storage-f0/Sources/BrowserCore/LifecycleCoordinator.swift#L217) · [Adapter retirement](../../../../../apps/browser-macos/StorageRuntime/Sources/BrowserNativeStorage/NativeWebKitStorage.swift#L293) · [Host error path](../../../../../apps/browser-macos/Sources/Host/MainWindowController.swift#L313)
4. The termination handler records `terminated-fenced` even when it matches no owned view. The current callback resolves the matching view's pending navigation only. Separately, the favicon task can await JavaScript and checks document identity and URL on return without an explicit fence check at that point. These are evidence and ordering gaps. The current source review establishes neither cross-scope access nor a runtime leak. Qualification must observe a matching callback, a denied old-scope operation, and harmless late or duplicate callbacks across reconstruction. [Termination trace](../../../../../apps/browser-macos/StorageRuntime/Sources/BrowserNativeStorage/NativeWebKitStorage.swift#L444) · [Asynchronous favicon path](../../../../../apps/browser-macos/StorageRuntime/Sources/BrowserNativeStorage/NativeWebKitStorage.swift#L402)

## Candidate for review

The viable design to investigate is an explicit private-session replacement for the affected window. Same-scope reconstruction conflicts with the existing poison fence. Directly creating a WebKit view would skip Core admission, store assignment and publication.

1. Keep the failed scope fenced. Detach its native surfaces and settle pending work through the existing ownership paths. Confirm successful Core retirement and empty old-scope inventory, including observed weak references. Revoke the old authority. If retirement is failed, timed out, or ambiguous, leave the window unavailable and record the exact condition.
2. On a single user action, create a new window-owned private scope with fresh run, store, grant and view identities through the existing private session factory and Core registration, resolve, activate and publish path. Verify the assigned store is nonpersistent before constructing the view. Do not remap a fenced store, reuse old view identities or transfer web state. [Private session composition and publication](../../../../../apps/browser-macos/StorageRuntime/Sources/BrowserNativeStorage/NativeStorageSession.swift#L50) · [Store assignment](../../../../../apps/browser-macos/StorageRuntime/Sources/BrowserNativeStorage/NativeWebKitStorage.swift#L146)
3. Preserve only reviewed in-memory workspace structure, such as ordered logical tabs, pins, group and Space membership, selection and split intent. Current UI state is keyed by ViewID, so the design must specify how logical identity maps to replacement view identities and rejects late callbacks. Each Mini stays in its own scope. Private bookmarks already clear on session change. Cookie values, login state, website storage, grants, form contents and browser back/forward stacks are outside the restoration contract. [Current identity ownership](../../../../../apps/browser-macos/Sources/Host/MainWindowController.swift#L31) · [Session bookmark lifecycle](../../../../../apps/browser-macos/Chrome/src/Browser.tsx#L106)
4. The existing requested URL can represent an uncommitted load. Keep unverified tabs blank. Any restoration navigation needs explicit user intent, a current policy check and a previously committed URL whose eligible request provenance is known. Never replay POSTs, redirect chains, credentials or request bodies. Stage reconstruction so another termination or failed publication cannot leave both old and new resources admitted. No automatic retries.
5. Prove one-window recovery before simultaneous cases. Record scoped termination, denied old-scope access, replacement store identity, actual page commit, workspace mapping, an unaffected window's isolation markers, and observed old-view release. Test interruptions and stale callbacks independently. If a partial replacement cannot be retired conclusively, keep the affected window unavailable.

This is a review proposal. It does not resolve whether Vezham should preserve the listed workspace structure across an explicitly disclosed private-session reset. The existing session-reset behavior remains the baseline until that boundary is reviewed.

## Why native fault injection stopped here

The WS-F5 runner can start an isolated host and kill its process group during cleanup. Its executable hash and host PID do not uniquely identify a WebKit content helper. The historical Phase 3 recovery used host-side diagnostic coalition and process identity evidence on the prototype, with three real terminations and 49 assertions. That evidence does not establish current host-to-helper attribution or distinguish a specific current main or Mini target before a signal. A helper may service multiple views. No process was signalled. [Current runner](../../../../../apps/browser-macos/Tools/wsf5.py#L176) · [Historical attribution and scope](../../../phase-3/phase-3-exit-review.md)

PR-01 is complete as a source investigation. PR-02 is blocked pending qualification of a defensible attribution method on this candidate. PR-03 through PR-10 remain unexecuted. The next review item is a bounded, test-only attribution design with a read-only two-host discrimination check, process identity revalidation at signal time, and an explicit abort when a target is ambiguous. The recovery change requires separate review of the lifecycle and workspace mapping above.
