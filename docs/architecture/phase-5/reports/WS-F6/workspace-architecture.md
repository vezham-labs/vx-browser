# Workspace architecture

**Implementation update · 10 November 2026.** The existing MainActor host is the mutation owner over a staged value model. It retains a private logical graph and a separate native binding map. A new repository/coordinator runtime is unnecessary for this in-memory scope. [Implementation report](implementation-report.md) · [Actual qualification](implementation-qualification.md)

**Classification: PROPOSED.** This is a target architecture for a separately authorized fixture-first implementation. [Baseline](current-state-assessment.md)

## Mutation and mount contract

Use separate counters for committed snapshot revision, mount generation, and Core's scope epoch. A change to durable layout increments one snapshot revision. Transient focus routing, allocation or page navigation cannot cause a layout save unless the command changes a persisted field. Do not send native capability tokens to chrome. Map a chrome logical ID to current native state at command execution. Page callbacks may update the matching volatile status. They cannot publish a different layout revision or authorize storage.

- **Create and reorder.** Allocate fresh workspace and default Space IDs in one mutation. Reordering and renaming preserve every identity. A create command creates an empty workspace; opening it is a separate explicit intent. Duplicate display names are allowed with destination labels that disambiguate their position.
- **Mount and switch.** A mounted workspace has one host and mount generation. Inactive workspaces keep logical layout only. Validate the destination, fence old mount requests, cancel pending loads and retire the source views through the owning lifecycle before admitting the target. If source retirement is uncertain, hold the mount unavailable and admit no target view. After confirmed retirement, an unavailable destination can be shown as a metadata-only error where authorized. Never attach a prior generation's view. A normal workspace switch within one authenticated library can reuse a window with the same profile. Opening a different profile requires explicit user intent and a separately assigned native window. The existing multiple-profile window acceptance criteria remain in scope for later qualification. [Engine contract](../../../browser-engine-contract.md#event-and-lifecycle-semantics) · [Profile gates](../../../browser-mvp-acceptance-criteria.md#profile-and-private-browsing-gates)
- **Remove.** A workspace must be empty, unmounted, and explicitly selected for deletion. The final workspace cannot be removed. Deleting a workspace removes its catalog row, layout and optional selection references together. It confers no website-data deletion authority. A Space must be empty and leave at least one Space in its workspace. Deleting a group ungroups its tabs in one revision. Closing a live tab is a lifecycle operation first, with separate logical removal and deterministic selection. If a later save fails, the prior snapshot remains readable and the tab will restore as a blank slot; an old view cannot return.
- **Order and moves.** Stable arrays encode order. A move references an existing destination and insertion position, with stale revision checks. Moving tabs within a workspace preserves their IDs, removes incompatible group/pair references and repairs affected active selections in one mutation. Cross-workspace tab transfer, simultaneous mounts of a workspace and multi-writer merge are excluded from F6.
- **Recovery.** An optional invalid selection can normalize within the graph. Structural errors preserve the original and prevent publication. A pending command is tied to its mount generation and operation, so duplicate or late work cannot affect a different workspace.

Authoritative commits return a revision and complete logical result to presentation. A denied or stale command returns the last authorized revision and an appropriate outcome. Candidate edits stay hidden during any uncertain persistence outcome. Chrome should distinguish blank, dormant, admitting, failed and scope-unavailable states instead of using missing `WKWebView` as an error predicate.

## Privacy and integration lanes

A private window's organization is a separate volatile object, outside the protected catalog and synthetic repository write paths. Do not use private snapshots as restore fixtures. Maintain the current WS-F5R recovery implementation and evidence during F6. Any later adoption of logical IDs by the product private path requires separate change review and renewed coverage of private teardown and recovery. The native fixture can use the existing private composition against generated layouts and owned origins with isolated test storage.
