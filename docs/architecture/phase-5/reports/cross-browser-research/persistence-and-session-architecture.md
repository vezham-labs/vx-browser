# Persistence and session architecture

## Separate the records by ownership

| Class | Vezham today | Recommended boundary |
|---|---|---|
| Global preferences | Ordinary SQLite is allowlisted for appearance | Keep the existing allowlist. Treat workspace names, URLs, titles and browsing-derived state as potentially sensitive |
| Workspace graph | Window memory, with tab identity tied to live `ViewID`; recovered blank layout exists only in memory | Versioned logical records for normal workspaces, with stable Space, group, tab and window IDs. Runtime bindings are transient |
| Navigation | Current view URL and requested URL serve live UI; recovery leaves slots blank | Use only policy-eligible, provenance-checked destinations for any future opt-in normal restore. Keep app-owned address, last committed page and pending request distinct |
| Website data | WebKit owns cookies, storage and cache, currently in a nonpersistent store for each private session | Bind each authorized profile to a verified WebKit store identifier. Record eligibility and lifecycle receipts in Vezham-owned state |
| Credentials and grants | Native Keychain/permission adapters and tests exist. Real profile unlock and durable grants are gated | Signed native key custody and explicit origin/frame/scope policy, revocation and lock. Browser encryption keys and saved website credentials have different uses |
| Backup | Owned authenticated archive and synthetic tests | Bounded, schema-versioned, selected browser-owned records. Import into a fresh protected destination with authenticated validation and an atomic publication step |

## Competitor approaches

- **Search** stores session rows and groups independently of live pages and wakes the visible selection. Named persistent stores and private tab stores have different paths. Plain JSON metadata is useful as a model illustration. It has a different protection posture from Vezham's approved storage architecture. Search's changelog records a close-time stale save that erased pins in other windows. Use a single versioned transaction owner and reject writes from closed generations. [Session format](https://github.com/driceroland/Search/blob/e198e77b6e57519d6ceb0d13a816757dffa586ad/Sources/Search/Session.swift) · [Store selection](https://github.com/driceroland/Search/blob/e198e77b6e57519d6ceb0d13a816757dffa586ad/Sources/Search/Spaces.swift) · [Close-time fix](https://github.com/driceroland/Search/issues/750)
- **Zen** extends upstream Firefox restore with sidebar records, migrations and backup fallback. A Firefox container can separate logins within a profile. Vezham can use explicit restore precedence and schema migrations, with profiles as WebKit data boundaries. Zen's compressed backups do not establish an encryption model for Vezham. [Zen session manager](https://github.com/zen-browser/desktop/blob/498360074520dcbc9aaa491f498a171a0fa6df07/src/zen/sessionstore/ZenSessionManager.sys.mjs) · [Workspace containers](https://docs.zen-browser.app/user-manual/workspaces)
- **Arc/Little Arc and SigmaOS** document migration, organization and product-level continuity. Historical Arc archive can include closed Little Arc links. SigmaOS advertises sync and separate cookies. Proprietary restore payloads, storage custody, encryption and window mappings remain unverified. Vezham Mini should continue to leave no durable private history or session record. [Arc export](https://resources.arc.net/hc/en-us/articles/25583851606039-How-Do-I-Export-My-Data-from-Arc) · [Arc release history](https://resources.arc.net/hc/en-us/articles/20498293324823-Arc-for-macOS-2024-2026-Release-Notes) · [SigmaOS Workspaces](https://docs.sigmaos.com/tutorial/workspaces)
- **Cra, Stedding, Flecha and Vela** use browser contexts or partitions, and document or implement import across engines/products. Stedding's sync issue is an example of how multiple writers and stable identity matter even when syncing organization alone. Importing live credentials and cookies creates a much wider boundary than importing links. [Cra help](https://crabrowser.app/help) · [Stedding issue 89](https://github.com/ysalitrynskyi/stedding-browser/issues/89) · [Flecha browser importer](https://github.com/lucianodiisouza/flecha-browser/blob/e54caa21edcb21b8936d6424dae3887078e2a805/chromium/native-host/browserImport.ts) · [Vela session manager](https://github.com/JoSanson/vela/blob/55b18a3ad70dbf8838c4acf512230e57368ac2d2/apps/desktop/src/main/sessions.ts)
- **Refrax** defines shared, isolated and ephemeral profile specs for engines alongside host-owned history and settings. Shared host metadata is a separate layer from an engine's cookies and sessions. Use the ownership lesson and reject cross-engine profile translation. [Engine contract](https://github.com/kageroumado/refrax-browser/blob/a34ec67fe2ce384e09037f92227de224d3631c98/Engines/CONTRACT.md)

## WS-F6 model and restore contract

Restore a coherent workspace graph with explicit schema version and revision. Validate size, order, distinct identifiers, referential integrity, focus membership, and window frame visibility. Sanitize stale optional references deterministically and reject invalid or unsupported snapshots without overwriting their source. Use transactional publication, interruption testing, idempotent migration, and an older-reader refusal path. Reconcile with a single metadata owner when a window closes during a save. Window geometry is an optional part of the graph with deterministic fallback for changed displays.

Maintain a strict separation between private in-memory recovery, normal restart restoration and import. Keep the current private blank-layout recovery and its session generation boundary. Private records, URLs, cookie/cache state, history, form contents, grants and screenshots stay out of normal snapshots, backup, import/export and diagnostics. No POST, credentials, transient redirect or request body is replayed. For any later URL-based normal restore, define what counts as a safely committed navigation and whether selecting a dormant tab is sufficient user intent. Make the first visible load auditable. [Current recovery policy](../WS-F5R/recovery-design/workspace-restoration-policy.md)

WS-F6 can qualify the graph with synthetic fixtures after WS-F5R. A product write of real workspace metadata requires the protected catalog and signed key gates. WS-F7 must test missing/wrong key, corrupt and interrupted migration, lock/clear/delete during save, same-site isolation, and backup tamper/rollback behavior against the approved provider path. WebKit stores, credentials, and browser metadata have independent portability and retention rules. [Approved decisions](../WS-F3/approved-decisions.md) · [Next gates](../WS-F3/next-gates.md)
