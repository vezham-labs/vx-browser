# Privacy and security comparison

## Isolation and custody

| Reference | Evidence | Implication |
|---|---|---|
| Vezham | Private windows use separate nonpersistent stores. Within a window, tabs, Spaces and split panes can share the session. Core/native authority and generation checks gate use. Native key broker and permission mediator are implemented with blocked product and positive runtime cases | Describe separation at the window/session level. Independently test same-origin cookies, LocalStorage, HTTP cache, service workers/IndexedDB as applicable, and denied work after lock, close or termination |
| Search | Source selects nonpersistent stores for private tabs and persistent stores by its Space/profile model. The vault uses macOS Keychain. Rule-list enforcement and download delegate are implemented | Useful public WebKit primitives. Its private granularity, credential UI, metadata file format, and private APIs elsewhere carry different risks |
| Arc and Little Arc | Vendor documents profiles, privacy and history; historical wrong-profile routing and Little Arc archive are observable product disclosures. Source and exact credential/permission/backup behavior unavailable | Make the destination and retention policy visible. Avoid extrapolating a separate temporary-window cookie or process model |
| SigmaOS | Vendor claims Apple Keychain and WebKit tracking prevention, documents separate-cookie Workspaces and extension installation. Permission and backup internals unavailable | Treat claims as a guide to questions, and verify each privacy boundary in Vezham's own configuration |
| Zen | Firefox container model with shared profile history and extensions per Zen docs. Firefox content processes and browser chrome remain separate concepts | Use explicit terminology for login/store isolation, UI organization and process sandboxing |
| Cra, Stedding and Flecha | Cra has CEF context paths and Safe Storage Keychain code. Stedding's independent Space uses a Chromium storage partition and retains some shared profile state. Flecha adds partitioning and a secret-capable import surface | Partition-aware UI is useful. An engine-specific importer and stored credentials carry significant authority. Use metadata-only migration if later justified |
| Refrax and Vela | Refrax source includes per-mode stores, Space lock and Keychain password manager. Vela uses Electron partitions, sandboxed page preferences, permission prompts and import paths | Review each host's independent storage and control assumptions. A Space lock or sandbox flag alone cannot establish Vezham's profile or secret-handling guarantees |

## Native WebKit controls

Vezham should require explicit store assignment and refuse unknown identity or unexpected default-store fallback. Lock and recovery should revoke grants and invalidate stale UI or extension handles. Permission decisions should bind to origin, frame, current document, scope generation and relevant native authorization. Display the requesting origin and support denial, cancellation and revocation before broadening positive routes. Compare a controlled main/subframe redirect, tab close or replacement during a prompt, private vs. profile, and sleep/lock transitions. Document browser-owned records separately from website data; qualify available WebKit clearing behaviors by data category and OS. A key lease protects authorized access to Vezham-owned data. It provides no guarantee of physical erasure or app-controlled encryption of WebKit storage. [Native mediator](../../../../../apps/browser-macos/StorageRuntime/Sources/BrowserNativeStorage/NativePermissionMediator.swift) · [WS-F3 WebKit storage](../WS-F3/webkit-storage.md) · [WS-F3 Keychain and signing](../WS-F3/keychain-signing.md)

Tracking prevention, declarative blocking and permission mediation are different controls. WebKit publishes tracking-prevention behavior, but the actual policy must be verified in Vezham's embedding and supported macOS versions. Investigate a small public `WKContentRuleList` fixture with reproducible compile/apply, versioning, disable/rollback, per-site exception scope and page-breakage tests. List distribution, attribution, privacy of exceptions and operational update cost need separate review. Use the content-rule mechanism instead of inventing a general request interceptor. Test redirects, third-party cookies and storage, subframes, service workers, downloads and first-load timing. [WebKit tracking prevention](https://webkit.org/tracking-prevention/) · [WebKit content blockers](https://webkit.org/blog/3476/content-blockers-first-look/) · [Search Shield](https://github.com/driceroland/Search/blob/e198e77b6e57519d6ceb0d13a816757dffa586ad/Sources/Search/Shield.swift)

## Highest-risk expansions

Cookie/password extraction from another browser, private data in exports or automation, credential exposure to web chrome, and unrestricted injection or native messaging create high-impact access paths. Keep those outside release scope. Use Keychain for native custody under the repository's signed and scoped policy. Treat the password manager, protected database keys, permission grants, and website authentication cookies as separate assets. WebKit process isolation reduces exposure within engine boundaries. The native app and any authorized extension or automation bridge still need separate least-privilege checks.
