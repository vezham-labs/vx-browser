# WebKit, Chromium and Gecko lifecycle comparison

| Layer | WebKit embedding | Chromium family | Gecko and Zen |
|---|---|---|---|
| Unit the host owns | `WKWebView` and its configuration. Vezham owns admission, attachment, metadata and store identity. WebKit controls helper allocation | Chromium owns renderer processes and site isolation. CEF exposes embedded browser and request-context handles. Electron exposes WebContents and Session. Forks can modify tab or renderer policy directly | Firefox/Gecko owns browser elements, browsing contexts and Fission process selection. Zen patches that browser stack |
| Storage | Assign explicit persistent identifier or nonpersistent store before construction; a store is the website-data boundary | Profile, off-the-record context or storage partition, depending on embedder. A renderer or visible Space alone says little about site data | Profile, contextual identities and private mode use distinct mechanisms. Container assignment can be associated with a Workspace |
| Deferred work | App can keep logical records without allocating views, construct visible selection on demand, detach or retire under policy | Arc documents background optimization. Stedding/Flecha can use Chromium policies and patches. Vela source creates views on demand and drops eligible hidden views. Cra can control CEF browser construction | Firefox SessionStore persists tab/window state. Zen integrates separate sidebar state and backups. Exact upstream scheduling varies with build and prefs |
| Failure | Public delegate tells the app which view notified. It does not supply a reliable helper PID or a contractual one-view/one-process mapping | Chromium has renderer crash handling; Cra handles CEF termination, Vela observes `render-process-gone`. Fork/product recovery remains separate from the engine callback | Firefox process isolation and session state are available to the browser. No Zen-specific crash behavior was reproduced |
| Portability | Public API and macOS-version gates. No engine patch or helper bundle required | Bundling, patch/update cadence, signing, helper management and Chromium-specific APIs depend on host architecture | Gecko chrome APIs, Fission, Firefox storage and SessionStore cannot be reused as WebKit APIs |

## Search as the nearest source comparison

Search separates tab metadata and the optional built page. Restore reads saved rows, groups and splits, chooses the front tab, then wakes the visible tab or split members. Persistent site stores and per-private-tab nonpersistent configuration are selected before construction. Sleep can release an existing view, subject to exclusions for active use such as media/capture, downloads and unfinished input. Cold restore and sleep are two different policies. The latter can lose in-page state and needs a stronger oracle. Search handles both the public termination callback and a private reason callback, reloads visible tabs within its recovery policy and marks hidden tabs stale. Vezham can learn from the lazy model and the bounded failure UX. Its private poison fence and blank replacement remain the governing policy. [Search Tab](https://github.com/driceroland/Search/blob/e198e77b6e57519d6ceb0d13a816757dffa586ad/Sources/Search/Tab.swift) · [Restore](https://github.com/driceroland/Search/blob/e198e77b6e57519d6ceb0d13a816757dffa586ad/Sources/Search/Browser.swift#L2684) · [Sleep](https://github.com/driceroland/Search/blob/e198e77b6e57519d6ceb0d13a816757dffa586ad/Sources/Search/Sleep.swift) · [Termination](https://github.com/driceroland/Search/blob/e198e77b6e57519d6ceb0d13a816757dffa586ad/Sources/Search/Dialogs.swift#L364)

Cra's primary path is CEF even though the same AppKit shell also offers a narrow WebKit media path. That source shows separate per-engine commands, popups and extension behavior. Refrax makes the distinction a whole engine contract with profile specs, events and external bundles. Refrax also initializes its restored window without selecting a tab or building a page, leaving activation to the user. These are useful examples for keeping existing Vezham ports small and recording capability failures. Their engine bridge, plugin model and extra update surface are out of scope. ## Vezham lifecycle proposal

1. A restored logical record begins dormant with no native handle. Resolve its current authorized scope when it becomes visible. Deduplicate concurrent activation per record and scope generation.
2. Build through existing Core registration/resolution, store assignment, activation and publication. Bind the resulting `ViewID` to logical ID and generation. Publish current state only after the authoritative result. A failed creation leaves the slot dormant or visibly unavailable.
3. A split may admit two distinct visible records in the same eligible scope. A compact split admits the focused member first. Inactive records should generate no requests during initial restore. No claims about one process per visible tab follow from view counts.
4. Keep live, detached, dormant, retiring and fenced state distinct. Initial lazy admission does not require automatic eviction of live tabs. Assess eviction later after measuring state loss and validating guards for focus, audio/video, capture, downloads, pending permission and unsaved interaction.
5. A termination invalidates the scope generation and blocks old handles. Retain retirement and revocation postconditions. The existing callback-qualified recovery stays an independent workstream. Consider lazy replacement only after WS-F5R and with a newly qualified reconstruction path.

Prove zero background store/view/navigation actions at restore, focus-switch deduplication, close during activation, missing/locked store, app quit, fallback on compact layouts, and rejection of a stale callback after rebinding.
