# WKWebView Native Feasibility Prototype Report

**Date:** 2026-11-07  
**Status:** Authorized local/public feasibility investigation completed; full Phase 3 acceptance remains open with explicit blockers.  
**Engine decision:** WKWebView remains Proposed. ADR 0001 is unchanged.

## Executive summary

A small native Swift/AppKit prototype was created under [`prototype/wkwebview`](../../../prototype/wkwebview/README.md). It compiles against the installed macOS 27.2 SDK while targeting macOS 26.0. The bundle was ad-hoc signed with Hardened Runtime enabled and the prototype App Sandbox entitlements; `codesign --verify --strict` passed.

The initial launch attempt failed with `kLSNoExecutableErr` (`-10827`) and direct execution aborted before the main-entry diagnostic. After Xcode 27.2 was installed and selected, the app entered its AppKit run loop and the loopback storage harness completed. Seed and fresh-process verification reports recorded zero failures for the tested synthetic storage markers and data deletion. The earlier launch error was not reproduced, but its cause is unknown. The app retained App Sandbox and Hardened Runtime; no security setting was removed or relaxed. These results cover macOS 27.2 only and **do not pass the complete product acceptance gates**.

In addition to compile/link and static signature verification, the loopback storage, find/zoom, upload, isolated download, and visible download save-panel harnesses ran successfully on macOS 27.2. They reported bounded observations for persistent profile storage, cache reuse, data deletion, private-window lifecycle, find configuration, per-view zoom, a synthetic attachment download, one native upload-panel selection, and one native download-panel selection. The original crash-recovery runner stopped safely because it could not tie a WebKit process to the isolated app; it terminated no process. A later local interaction run passed 13 checks for both native panel cancellations, one HTTP 302, one same-origin private popup, and an unsupported-scheme rejection; see the retained evidence in [test results](wkwebview-test-results.md). The full product acceptance gates remain incomplete.

## Implemented prototype capabilities

- Native AppKit window, address entry, back/forward, reload/stop, progress, navigation status, and error status.
- `WKWebView` embeds remote content in a view separate from native browser controls.
- Main-frame and popup navigation accepts only HTTP(S); popup requests open a native window assigned to the originating profile/session.
- Persistent profile stores are created by stable UUID identifiers for Profile A and Profile B.
- A private session uses one `WKWebsiteDataStore.nonPersistent()` store shared across its windows. A headless AppKit lifecycle harness exercised the close callbacks: closing one window retained the shared session, and closing the last caused the registry to create a new session. OS-managed transient-data cleanup remains unverified.
- Prototype upload/download paths use native panels and app-owned temporary staging. The destination is populated only after WebKit completion; failed staging is removed. Synthetic completed/interrupted behavior passed focused regression checks. Normal window/app shutdown cancels active transfers and removes tracked staging; abrupt process death and remaining destination cases still require validation.
- Find-in-page and per-view page zoom are wired to public WebKit APIs.
- Source implements an origin-labelled native camera/microphone prompt. With OS access temporarily authorized, the final native Deny request passed 4/4 checks and the page received NotAllowedError/no stream. Actual website grants, persistence/revocation and independent device cases remain unverified; unsupported permission types have no product implementation.
- Content-process termination is surfaced with a reload recovery action. The prior single-view automatic-reload harness passed 30/30 crashes. The final revision passed 49 actual-window recovery checks across A/B/Private, including toolbar Reload and injected stale/foreign navigation callbacks. Durable state and broader in-flight crash cases remain unverified.
- App logging records event names and host only; URL path, query, cookies, page content, credentials, and local file paths are not logged by the app logger.
- A versioned, typed native `BrowserCommand` envelope is used by AppKit controls. This is an in-process prototype boundary, not the production React-to-Swift bridge. No page message handler or generic page-to-native bridge is registered.
- The local test harness observed synthetic cookies, localStorage, IndexedDB, Cache Storage/service-worker state, persistent A/B separation across a fresh process, same-profile HTTP-cache reuse, concurrent views sharing a store, and website-data deletion. A separate headless AppKit test exercised actual private-window close callbacks and verified registry session replacement after the last window closes. OS-managed transient-data cleanup remains unverified.

No React/HeroUI view, `@vezham/aura`, Go service, Tamizhi, Vezham ID, sync, history product, extension system, or production browser state store was added.

## Security observations

- **Remote content boundary:** Native AppKit owns browser controls; website content receives a separate WKWebView. No website-facing message handlers are installed, and the loopback fixture observed no `vezham` handler in its tested views. This removes that bridge from the prototype, but dynamic adversarial origin/frame verification is pending.
- **Navigation:** URL normalization, direct unsupported schemes, same- and cross-origin HTTP redirects/popups, a cross-origin hostile frame, and privileged-shaped frame/top-level schemes have bounded evidence. One hundred forged/oversized messages found no native page channel. This does not validate a future production React/native transport, all origins, certificate-negative cases, or a general firewall.
- **Profiles:** Separate persistent store UUIDs and a shared per-private-session nonpersistent store are implemented. The macOS 27.2 harness and a bounded post-exit app-container scan found no private marker in WebKit's persistent store directory; no isolation guarantee is confirmed until the harness also runs on macOS 26 and the current supported macOS 26.x release.
- **Process isolation:** WebKit process management is platform-owned. This prototype does not demonstrate per-profile renderer separation and makes no such claim.
- **Credentials:** No account token or Keychain credential is stored or injected. Keychain boundary testing is not performed.
- **File access:** Single/multiple-file and directory selections, cancellation, duplicate-name cancellation, and interrupted/completed transfers have synthetic evidence. An incomplete-final-file defect was fixed using app-owned staging and verified by 9 executed checks. Cross-volume, overwrite-completion, metadata/quarantine, symlink, abrupt-host-death and long-lived scope behavior remain unverified.
- **Permissions:** With both OS permissions authorized for the disposable app, the origin-labelled Vezham prompt appeared and explicit Deny returned NotAllowedError/no stream: 4/4 final-request checks passed. An earlier request chose Allow in the app prompt but the denial-only guard returned Deny; its original 3/4 result is retained separately. Targeted OS resets succeeded after app closure and the build was removed. Real website grants, persistence/revocation and separate device cases remain unverified. The test mode forces Deny even if the default Allow button is selected accidentally; the report separately checks an explicit Deny choice. OS status diagnostics read authorization values without requesting or recording media.
- **Logging:** App-owned messages avoid full URLs and sensitive values. OS-generated WebKit, crash, and diagnostic logs were not inspected or validated for redaction.
- **Sandbox:** Entitlements present in the normal ad-hoc signed bundle are `com.apple.security.app-sandbox`, `com.apple.security.network.client`, and `com.apple.security.files.user-selected.read-write`. The separate permission-test bundle temporarily added camera and audio-input entitlements with matching purpose strings. No Keychain group or broad filesystem entitlement is requested. Runtime entitlement enforcement is not verified.

## Recommendation

**Continue WKWebView investigation; do not approve the engine from this evidence alone.** The authorized local/public investigation and review package are complete, including the discovered incomplete-download fix. Remaining Phase 3 items include account workflows blocked by user direction, grants/revocation, remaining product-state/UI/bridge/transfer cases and controlled performance coverage. Bounded crash recovery and aggregate RSS now have host-specific attributed evidence. At the user's direction, developer code signing/notarization and macOS 26 runtime validation are deferred to the final release-validation stage; they are not current Phase 3 blockers and remain unverified release conditions. The minimum stays macOS 26.0. ADR 0001 stays **Proposed** until review and explicit product-owner approval; no Phase 5 production engine implementation was started.

## Distribution and updater review

Accepted ADR 0002 requires Developer ID Application signing, notarized internal direct-distribution artifacts, and Gatekeeper compatibility. A future updater must verify signed metadata and artifact integrity, provide replay and anti-downgrade defenses, support key rotation/emergency revocation, separate channels, stage rollout, and allow safe rollback without reinstalling revoked vulnerable builds. This prototype has no installer or updater; those mechanisms remain unselected.
