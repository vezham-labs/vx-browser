## Test protocol and run evidence

The latest storage run used a temporary build and unique app identity `internal.vezham.WKPrototype.Isolation.1794010663.1284`, preserving the normal prototype bundle and container. Its [seed report](<../../../prototype/wkwebview/Evidence/isolation-results-20261107T001743Z-1284-seed.json>), [fresh-process verify report](<../../../prototype/wkwebview/Evidence/isolation-results-20261107T001743Z-1284-verify.json>), and [private-window report](<../../../prototype/wkwebview/Evidence/window-lifecycle-results-20261107T001743Z-1284.json>) report zero failures (12, 6, and 3 observations). A second Profile A view reused the cache generation, while Profile B returned its own cookie-derived response from the same URL. The headless AppKit lifecycle check closed one private window while retaining the shared session, then closed the last window and observed the registry create a new session. Persistent A/B markers survived a fresh process and website-data deletion cleared them. Each fixture observation reported `bridgeAbsent=true`; this confirms no `vezham` message handler was visible to those test pages, not the safety of a future React bridge.

The fixture uses `http://127.0.0.1` and no real authentication, certificates, external hostnames, or user data. These observations are from macOS 27.2 only. The lifecycle test exercises actual `NSWindow` close callbacks. After the latest isolated app exited, a bounded scan of its `Library/WebKit/WebsiteDataStore` found only the persistent Profile A/B UUID directories and no `marker-private` value. OS-managed temporary files outside the app container were not inspected.

The latest find/zoom harness used a separate ad-hoc signed app identity and temporary build directory so it did not replace the existing prototype bundle. Run `20261107T002129Z-1533` recorded 14 passing checks on macOS 27.2 (26B123), with zero failures. Its [JSON report](<../../../prototype/wkwebview/Evidence/find-zoom-results-20261107T002129Z-1533.json>) records view-scoped zoom, find case handling, previous/next, wrapping, and zero-result behavior. The UI's find field remains forward-only, case-insensitive, and wrapping; it has no clear/stop action or explicit zoom-reset button. The macOS 26 runtime baseline is deferred until after the other roadmap phases and remains unverified.

The isolated download harness used a separate ad-hoc signed app identity and a loopback-only synthetic attachment. Run `20261107T002200Z-1650` recorded five passing checks with zero failures. Its [JSON report](<../../../prototype/wkwebview/Evidence/download-results-20261107T002200Z-1650.json>) shows that WebKit handed off the attachment, reduced the path-like suggested name to `_.._synthetic-download.bin`, kept the destination inside the isolated directory, and saved bytes identical to the fixture. This harness used a test destination and did not open the visible save panel.

The separate native download save-panel run `20261107T080255Z-9290` passed three checks. The [JSON report](<../../../prototype/wkwebview/Evidence/download-panel-results-20261107T080255Z-9290.json>) records the selected file `_.._synthetic-download.bin`, an isolated-folder destination, and 34 bytes identical to the loopback fixture. The panel visibly identified `http://127.0.0.1:18765` as the source. Cancellation was not covered in that selection run; see the later interaction evidence below. Duplicate names and arbitrary user-selected destinations remain untested.

The upload-picker harness used temporary identity `internal.vezham.WKPrototype.Upload.1794038136.7994` and a single generated file. Run `20261107T075536Z-7994` passed three checks: the fixture received `upload-fixture.txt`, verified the exact 32-byte payload, and confirmed the request stayed on loopback. The [JSON report](<../../../prototype/wkwebview/Evidence/upload-results-20261107T075536Z-7994.json>) records zero failures. This exercises one native open-panel selection only. Cancellation was subsequently covered by the interaction run; multiple files, directory selection, and security-scoped URL lifetime remain untested.

Source review found that an unknown future `WKMediaCaptureType` fell through to the same one-time Allow/Deny prompt as known types. The handler now denies unknown types immediately. Permission alerts and native upload/download panel messages show the requesting origin including scheme and port. A temporary build and ad-hoc signature verification passed after these changes. The native upload open panel and download save panel were each exercised once with synthetic files; the app-level permission prompt remains unverified.

The URL input policy test uses the same Foundation helper as the app and recorded 13 passing cases on macOS 27.2 while targeting macOS 26.0. Its JSON evidence is [url-policy-results.json](../../../prototype/wkwebview/Evidence/url-policy-results.json). The test checks normalization and scheme/credential rejection only; it does not test WebKit redirect, popup, or subresource handling.

The latest denial-only media attempt, run `20261107T084857Z-14398`, used `http://localhost:18765/permission-fixture` and a separate ad-hoc signed test app with temporary camera/microphone entitlements and purpose strings. User-supplied [microphone](../../../prototype/wkwebview/Evidence/permission-deny-20261107T084857Z-14398/microphone-prompt.png) and [camera](../../../prototype/wkwebview/Evidence/permission-deny-20261107T084857Z-14398/camera-prompt.png) screenshots visibly identify macOS privacy prompts for VezhamWKPrototype with Don't Allow/Allow buttons. In the preceding run, the user confirmed choosing Don't Allow; in this capture retry, automation observed the page change to Request denied, and the raw result records `NotAllowedError` and no stream. It still reports 2/4 checks passing because there are no app-owned prompt/decision events or event-log file. This verifies that both OS prompts surfaced and the combined audio/video request was denied; it does not independently verify each device's final privacy setting, a camera-only/microphone-only request, the WKUIDelegate prompt, allow, or revocation. The standard prototype entitlements were not changed.

The native interaction run `20261107T090509Z-15825` passed 13/13 checks on macOS 27.2 while targeting macOS 26.0; its [raw JSON](../../../prototype/wkwebview/Evidence/local-interactions-20261107T090509Z-15825.json) retains the native callback events and fixture observations, with [source hashes](../../../prototype/wkwebview/Evidence/local-interactions-source-20261107T090509Z-15825.json). Cancel in the upload panel returned nil/zero URLs, the page FileList remained empty, and the fixture counted zero uploads/bytes. Cancel in the save panel returned no destination, WebKit reported NSURLErrorCancelled (-999), and the isolated destination stayed empty. The UI displayed Download cancelled after correcting its generic failure label. One same-origin HTTP 302 and one popup retained the synthetic localStorage marker/cookie; the popup used the original native private data store and label. Both result pages reported bridgeAbsent=true. One unsupported custom scheme was cancelled while the fixture remained current. This is bounded loopback evidence; cross-origin, malicious-frame, arbitrary-path, and full permission-lifecycle guarantees are not established.

An [earlier incomplete run](../../../prototype/wkwebview/Evidence/local-interactions-incomplete-20261107T090022Z-15063.json) recorded 12/13 checks; the unsupported-address action was not reached before closing the delayed fixture run. The test fixture was changed to handle browser connections concurrently, and runner requests received time limits before the successful repeat. The earlier report is retained as failed/incomplete.
