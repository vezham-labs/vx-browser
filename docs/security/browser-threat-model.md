# Vezham Browser Threat Model

**Status:** Maintained threat model under the approved architecture baseline; risks and controls require staged implementation/release evidence  
**Scope:** Internal-only macOS 26 Tahoe+ product; untrusted web content; React/TypeScript + HeroUI v3 browser UI; Swift/AppKit host; phased Tamizhi; optional Vezham ID/cloud sync. `@vezham/aura` is excluded. This model does not certify either engine as secure. Measurable validation gates are in [the browser MVP acceptance criteria](../architecture/browser-mvp-acceptance-criteria.md).

## Security objectives

- A compromised page or renderer cannot read browser UI state, other profiles, credentials, local files, or privileged app data.
- Users can understand and control site permissions, file transfer, AI page access, and cloud sync.
- Profile boundaries are enforced in engine storage and app-owned state.
- Browser engine and helper processes run with the least privileges compatible with their role.
- Engine crashes, malicious pages, or sync failures do not silently expose or corrupt unrelated browser data.

## Assets and trust boundaries

### Assets

- Vezham ID access/refresh tokens, Keychain items, account identifiers, and device keys.
- Website cookies, HTTP authentication, local storage, IndexedDB, service-worker data, and caches.
- Browser history, bookmarks, downloads, open tabs, profile labels, and permission decisions.
- Page content, selected text, screenshots, DOM-derived data, and AI prompt/response data.
- Downloaded files, upload selections, file bookmarks, and user-selected paths.
- Engine update artifacts, code-signing credentials, helper entitlements, and release pipeline secrets.

### Boundaries

1. **Web renderer to browser host:** untrusted page content and scripts must not call arbitrary native methods.
2. **React browser chrome to native host:** the app-owned UI communicates through a versioned, typed allowlist; Swift validates and authorizes each request. The chrome surface must not load remote content, and UI-origin XSS is treated as a privileged compromise.
3. **Browser core to engine adapter:** core owns profiles, durable history, permission/download policy, and orchestration. The adapter translates core policy into engine calls and reports capabilities; engine objects and private APIs do not leak into product state.
4. **Native host to remote content:** website views are a separate untrusted surface with no privileged app message handler, account tokens, browser UI DOM, or unrestricted filesystem access.
5. **Renderer to browser/OS services:** WebKit or Chromium brokers network, filesystem, GPU, and device requests under engine and OS policy.
6. **Profile to profile:** site state, app history, permissions, downloads metadata, and sync records are profile-scoped.
7. **Local app to optional cloud services:** Vezham ID and sync may transmit account or profile data outside the device; local browsing cannot depend on them.
8. **Page content to Tamizhi:** explicit user action may move minimized page-derived information to the intelligence layer and, only under the disclosed mode, to remote AI infrastructure.
9. **Build pipeline to internal app distribution:** engine frameworks/helpers, licenses, signing identity, and update artifacts enter the app. Accepted ADR 0002 requires Developer ID Application signing and notarized internal direct-distribution artifacts; updater, installer, and exact sandbox details remain implementation decisions.

## Threat actors and assumptions

- Malicious or compromised websites, ads, redirects, downloads, and embedded frames.
- A renderer exploit attempting to escape process restrictions or access another tab/profile.
- A compromised extension, if extensions are introduced later.
- Malware or another local user with access to the same macOS account; the MVP does not claim protection against a fully compromised OS account.
- A hostile or compromised network/cloud endpoint.
- An AI prompt-injection page attempting to instruct Tamizhi or induce the browser to disclose data.
- Build/release dependency compromise or stale engine security fixes.

Assume web content is hostile from first byte. Treat a renderer as compromised for design purposes; Chromium’s own sandbox guidance uses this assumption. [Chromium sandbox design](https://chromium.googlesource.com/chromium/src/+/main/docs/design/sandbox.md)

## Engine-specific security notes

### WebKit

WebKit’s public API reports web-content process termination and documents a separate process for web content. Vezham should treat WebKit’s process isolation as platform-managed and avoid assuming that the host app’s sandbox entitlements are a configurable per-tab WebKit policy. For App Store distribution, App Sandbox is required; it limits the host app’s access but does not eliminate renderer or bridge risks. [Web-content process termination](https://developer.apple.com/documentation/webkit/wknavigationdelegate/webviewwebcontentprocessdidterminate%28_%3A%29), [App Sandbox](https://developer.apple.com/documentation/security/app-sandbox)

### Chromium through CEF

Chromium’s model separates the browser from renderer processes and uses OS sandboxing; CEF packages helpers but requires Vezham to correctly configure the macOS sandbox, signing identities, and role-specific entitlements. Renderer/GPU processes may need JIT-related hardened-runtime entitlements, which should be granted only to the processes that require them. Do not cargo-cult Chrome signing entitlements: CEF’s own signing guidance says identity-specific Chrome entitlements should not be copied. [Chromium architecture](https://www.chromium.org/developers/design-documents/multi-process-architecture/), [CEF sandbox](https://chromiumembedded.github.io/cef/sandbox_setup), [CEF code signing](https://chromiumembedded.github.io/cef/code_signing.html)

## Staged security requirements

The [owner decision](../architecture/phase-3/owner-approval-decision.md) conditionally accepts WKWebView for MVP planning/implementation and approves bounded closure/architecture. ADR 0001 remains Proposed. The separately authorized [WS-F2 storage/security milestone](../architecture/phase-5/reports/M1/m1-wsf2-closeout.md) extends the native host with bounded storage/security components; protected catalog/key/permission/backup gates remain incomplete. No privileged website bridge or production optional-service integration is added.

Stage A reviews bounded evidence, unresolved risks and critical workflows. Stage B validates the affected production boundaries and behavior before reliance. Stage C validates the actual signed/notarized candidate on macOS 26.0/latest supported 26.x, including release protections/performance/compatibility/updater security. Retain the following obligations at their applicable stage:

1. Confirmed product baseline: macOS 26 Tahoe+ and internal-only distribution. Follow accepted ADR 0002 for Developer ID signing/notarization; decide installer/updater details and validate hardened runtime, App Sandbox, and entitlements before a distributable build.
2. App Sandbox and hardened-runtime policy, with a written justification for every entitlement/exception.
3. Profile isolation matrix and private-profile data deletion semantics.
4. Permission inventory, default behavior, persistence duration, and OS TCC prompt behavior.
5. A bridge policy forbidding general page-to-native calls and exposing no secrets to page JavaScript.
6. Download/upload UX and filesystem access model.
7. Before any separately approved future Tamizhi feature: content-access scopes, destination disclosure, retention policy and data minimization. Production integration is excluded now.
8. Before optional identity/sync is separately enabled: data inventory, token/key storage, opt-in defaults, revocation and deletion. They are not local-browsing prerequisites.
9. Engine update SLAs and security response owner. If CEF is selected later, include helper signing, sandbox verification, license notices, and urgent Chromium patching.

This threat model is a design baseline, not a security certification. Independent review and adversarial testing are required before an internal release; no public distribution is authorized. Cross-profile/private leakage or unauthorized native access remains a hard failure, not an accepted exception.
